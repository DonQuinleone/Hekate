# Decisions

A running record of decisions that shape Hekate. Add new entries at the bottom; do not rewrite old ones, supersede them.

## 001. Fresh start

Hekate is a new codebase. There is no data migration from the legacy application, and no code, names or branding carry over from it.

## 002. TypeScript end to end

React, Vite, TanStack Router and Query, shadcn/ui on Tailwind (restyled heavily, not stock) on the web; Hono on the server with types shared through `packages/shared`; PostgreSQL with Drizzle; pg-boss for jobs; a built-in ffmpeg worker; Vidstack, wavesurfer.js and pdf.js for media; Better Auth. Not Next.js: the app is a single-page application served by the API, which keeps deployment to one image.

## 003. Deployment

One app image plus PostgreSQL and Caddy, via Docker Compose. Local storage by default, optional S3-compatible storage. Caddy terminates TLS.

## 004. Anchored comments and project profiles

Every comment has an anchor: a time range or frame, a region on a page or frame, a bar and beat, or a track or movement. Projects choose a profile (Music, Video, General) that decides which tools appear. The data model is the same for all profiles.

## 005. Multi-tenancy from day one

Every tenant-owned row carries an `organisation_id`, and every query is scoped by it. A self-hosted install has a single organisation by default; a hosted offering can run many in one database.

## 006. Music review is the launch priority

The first complete experience is reviewing a recording against its score: bar-anchored comments, takes, movements. Video follows on the same model.

## 007. Brand: Signal

Dark, understated, one signal colour (`#F0762E`), hairlines over cards, Schibsted Grotesk and DM Mono, and a mark of two stems and a point. Chosen over three earlier, more theatrical directions that read as a classical-music-only tool. Details in `docs/brand.md`.

## 008. Licence

GNU Affero General Public License v3.0 only.

## 009. Domain vocabulary

Projects contain folders and files of any kind. Tracks have versions (edits) and variations (treatments such as dry and wet mixes). Takes are recording-session snippets kept as reference, never versions. There are no movements. Reviews are approvals (logged decisions) or feedback (comments only), run by configurable workflows with guests, groups and per-project roles. Full definitions in `docs/domain.md`; this supersedes the asset and version wording in 004.

## 010. Media security from day one

Reviewers receive encrypted, segmented streams and server-rendered tiles, never original files or plain URLs. Keys and segment URLs are short-lived and bound to the viewer's session. Files are encrypted at rest with per-file keys. Visible watermarks come first; forensic watermarking (A/B segment marking for streams, per-recipient marks on downloads) follows. Every access is logged. This is not DRM, and the design leaves room for commercial DRM on the same segments. Details in `docs/security.md`.

## 011. Waveform first; comments carry across versions

The waveform is the primary surface for audio; a score is optional. Engineer tools (spectrogram, metering, loudness, phase) are part of the product, computed by the media worker. Comments carry over between versions with mapped anchors and a before and after, and configurable categories (such as Noise) can defer a comment to a later workflow stage. Details in `docs/domain.md`.

## 012. Identity

Better Auth underpins sign-in. Members can use OIDC or SAML single sign-on, LDAP, passkeys and hardware security keys (up to five per account by default), or passwords where allowed; guests use magic links scoped to their reviews. Organisations set the policy. Details in `docs/security.md`.

## 013. Built-in QA for audio and video

Quality checks are a native part of Hekate, run by the media worker on every audio and video upload, not an import from another tool. Findings are versioned with the file, drawn on the waveform, spectrogram and timeline, and can become comments. Checks are configured by delivery profiles per project. The default spectrogram palette is the iZotope RX style *Cyan to orange* map. Details in `docs/domain.md`.

## 014. Production tools built in

Scheduling, personnel, venues, repertoire, live take logging, score marking with T-notation and edit plots, stage plans and patch lists are part of Hekate, reimplemented natively from the maintainer's ControlRoom desktop tool. They share the project's data with tracks, takes and reviews. Take logging is local-first so it works without a connection. ControlRoom's movements map to tracks within a work. Details in `docs/domain.md` (Production).

## 015. Video deliverables and reviewer permissions

Video uses deliverables, cuts and renditions, a concept separate from tracks in the interface but not in the tables: a deliverable is a track in a video project, its cuts are versions and its renditions are variations (decision 138). Every reviewer has an individual permission set (items, history, comment visibility, tools, downloads, access window, view limits, actions), with defaults per organisation and project. Edit decisions are optional, imported from an EDL, and a project can require one on upload.

## 016. How work lands

All changes reach `master` through pull requests with green CI; `master` is protected. Work proceeds from the ground up, each layer complete and tested before the next is built on it.

## 017. Multiple storage backends

Storage is a set of named, configurable backends (local disk and any S3-compatible service), not a single choice. Every stored object is a blob row that records its backend and key, so backends can be added and defaults changed without migrating existing objects. An instance has a default backend; an organisation owner can choose another for new objects. Backends never issue URLs to browsers: all bytes leave through the server's protected delivery path. Every driver passes one shared conformance suite, and CI runs it against a real S3-compatible server. This refines 003's "local storage by default, optional S3".

## 018. Encryption at rest: segmented envelope encryption

Every stored object is encrypted before any backend sees it: AES-256-GCM in 64 KiB segments (the STREAM construction), with a per-object data key wrapped by a per-organisation key, itself wrapped by the instance master key. Segments keep range reads cheap for audio and video seeking. Master-key rotation re-wraps organisation keys at start-up and never rewrites objects. The master key is mandatory configuration; losing it loses the stored media, so the documentation tells operators to back it up apart from the database and storage. Details in `docs/security.md`.

## 019. Background jobs in PostgreSQL

Background work runs on pg-boss in the app process, so self-hosting still needs only PostgreSQL. Each job type has one definition (a zod schema for its data and its retry policy) shared by senders and workers, and workers validate data again when they take a job. The worker can be turned off (`WORKER=false`) for API-only replicas. Media tools run with protocol and demuxer allow-lists, time limits and a private scratch directory (`docs/security.md`). Unreadable media is recorded as such rather than retried; infrastructure failures retry with backoff.

## 020. The access log is append-only in the database

The access log is enforced append-only by PostgreSQL triggers, not only by application code: updates are always refused, and deletes need an explicit, transaction-scoped purge setting. Events reference files, people and reviews by plain id and copy the actor's name and email, so the record survives deletions. Recording is awaited, so access is refused if it cannot be logged. Details in `docs/security.md`.

## 021. Resumable uploads, encrypted per chunk

Uploads are Hekate's own small chunked protocol rather than tus: fixed 8 MiB chunks line up with the encryption segments, so each chunk is encrypted on arrival and stored directly as a multipart part (S3 multipart, or parts on local disk) and no plaintext is staged on the server. Because chunks arrive in any order, a blob's SHA-256 is computed afterwards by a job that reads the file back through decryption. Uploads are limited to 10,000 chunks (78 GiB), the S3 part limit.

## 022. Streaming: HLS AES-128 now, with surround kept intact

Proxies are HLS with fragmented MP4 segments, encrypted by Hekate itself with the HLS `AES-128` method (whole-segment AES-128-CBC) rather than CENC `cbcs`. Every browser player supports `AES-128` through hls.js; `cbcs` needs Encrypted Media Extensions and, in practice, a DRM licence server. Segments are re-encrypted, not re-encoded, so moving to `cbcs` later for commercial DRM costs a packaging job, not a transcode. Audio is delivered as a stereo AAC monitoring rendition, a lossless FLAC rendition that keeps up to eight channels, and Dolby Digital or Dolby Digital Plus passed through untouched (so Atmos in E-AC-3 survives); the player picks what the browser can play. Playback links are signed tokens bound to the viewer's sign-in session. Details in `docs/security.md`.

## 023. The player is hls.js under Hekate's own controls

Vidstack, named in 002, is deprecated and in security-only maintenance; its successor, Video.js 10, had only just reached its first release and brings many packages Hekate does not need. Hekate drives a plain media element with hls.js instead, under its own controls drawn from the design tokens. The player needs little beyond play, seek, volume and a choice of rendition, and the waveform, spectrogram and comparison tools (#34, #44) will drive the same media element directly. hls.js is loaded only when a player opens. This amends 002.

## 024. Projects are visible only to those with a role in them

A project's roles are rows in its own `project_roles` table, each a set of permissions from the fixed list in `packages/shared/src/roles.ts`. Every new project is given the defaults from `docs/domain.md`, and its creator is its first Producer. An organisation member who holds no role in a project, or whose role lacks *view*, does not see the project at all: it is missing from their list and its routes answer 404, as they do for another organisation's project. Organisation owners and admins need no role and may do everything. Every project route asks one server-side check (`can` in `apps/server/src/access.ts`); the web app hides what a role cannot do but never decides it. Playback links are checked against the project on every request, so taking a role away ends playback at once. Any member may still start a project.

## 025. Guests sign in with single-use links and hold a separate session

A guest is a row in the organisation's `guests` table, found by email, never a Better Auth user. Asking a guest to review sends a magic link: a random token of which the database keeps only the SHA-256 hash, usable once, within three days unless the workspace chooses 14 or 30 in its settings, and revoked when a newer link is sent. Opening it spends the link atomically and starts a guest session (its own table and an httpOnly, SameSite Strict cookie) that lasts a fortnight unless revoked. Routes that guests may use (files, comments, reviews and playback) accept either a member or a guest; every other route still requires a member. A guest reaches only the files of the open reviews they are part of, may view, comment and decide on them, and never sees other reviewers' email addresses. Someone holding both a member sign-in and a guest cookie acts as the member. Revoking a guest ends their links and sessions at once.

## 026. A group is one step of a review, fixed when it is asked

Groups belong to a project and hold members and guests in order. Asking a group expands it into its people as they are at that moment, all at the same step (`review_reviewers.position`), each remembering the group they came through. In a sequence, everyone at the earliest step that is not finished acts together, and the next step starts once all of them have responded; the approval rule still counts every reviewer. Later changes to the group do not touch reviews already sent, and deleting it only drops the name. Someone named twice (alone and in a group, or in two groups) is asked once, at their first step. Members of a group must be able to see the project, and for an approval to decide, checked when the group is asked. Saving a group needs the "add or remove reviewers and guests" permission.

## 027. Deleting a folder keeps its files; a file under review stays

A folder's name is unique among its siblings (`NULLS NOT DISTINCT`, so at the top of a project too). Deleting a folder removes it and the folders inside it, and moves every file and track that was in them up to where the folder was: a folder is a way of arranging things, and removing the arrangement should not remove the work. Deleting a file is final, needs the "organise" permission, and is written to the access log in the same transaction; a file that is a variation of a track's version, or an item of any review, cannot be deleted, so what reviewers were asked about stays on the record. Its stored bytes go at the next storage reconciliation. Folder changes in a project are serialised on the project row, so two moves cannot together make a loop.

## 028. Content before chrome

Every page has one header bar: the trail back up (Projects / Joplin Rags / …) ending in the page's own name, which is its only title, with the page's actions on the right. Labels that only restate what is on screen (a project's profile, its anchor types, a status pill with no meaning) are left out. The sidebar earns its width: Reviews, with a count of those waiting on you, Projects with a short list of them, and Members; it collapses to icons (`[` or its button) and the choice is remembered. The organisation lives in the account area, where it can be switched. In a project, tracks sit among folders as a special kind of folder, and the files in a track's versions live in it rather than loose beside it. Files dropped anywhere on a project page upload to the open folder; the Upload button is the other way in. Row actions sit behind one menu shown on hover. The player opens on one waveform with the channels combined; split channels, the spectrogram (below, behind or instead of the waveform) and, later, the score are switched on from its View menu. Reviewers check new screens against established products (AGENTS.md, Interface).

## 029. A comment thread travels with the track, and is settled where it is fixed

A thread stays on the file it was raised on. Creating a version carries the previous version's unresolved threads to it, in the same transaction: each becomes a row in `comment_carries` on the new version's variation of the same name (the wet mix to the wet mix), otherwise its primary. The row holds where the thread points on that file, whether it shows there (the project decides the default; triage can hide or show it) and its status there: open, fixed, not fixed or won't fix. Fixed and won't fix resolve the thread itself; open and not fixed keep it going, so it is carried again to the next version. Until alignment between versions exists (#33), a carried anchor keeps the same times, and whoever triages can move it to the passage on the new version; before and after then plays the earlier version offset by the difference, level-matched, inside a loop around the passage. Replies written on any version join the one thread. People who cannot triage never see a thread hidden on their version.

## 030. A review grants each reviewer their own permissions

Every reviewer row holds a permission set (`review_reviewers.permissions`, validated by `reviewerPermissions` in `packages/shared`): whose comments they see (everyone's, their own and the replies to them, or only their own), whether they comment and record a decision, which tools they have (spectrogram, meters, loops) and an access window. A review can set everyone's when it is asked, and anyone who may manage reviewers can adjust one reviewer at a time. A guest gets exactly what the review grants; reaching a file through several reviews, they get the widest of them, but a decision belongs to one review. A member's project role stays the ceiling: the review can take a decision away, or close their window, but never adds to the role; their comments and tools follow the role, since they reach the same files through the project, so the review page offers only what applies. In an approval, a reviewer asked for no decision follows along: they neither hold up the order nor count towards the outcome. The server enforces all of it: comment lists are filtered, replies into an unseen thread refused, spectrogram and loudness data refused when the tool is left out, and outside the window a guest's files, review and playback are closed. Loops are an interface tool and only hidden. Organisation and project defaults, downloads and play limits follow.

## 031. Versions are aligned by their audio, and comments follow the music

Creating a version queues, for each variation of the previous version, an alignment with the variation its threads move to (`alignments`, one row per ordered pair). The media worker decodes both at 11,025 Hz mono, reduces each to fingerprints ten times a second (half the spectrum's shape in 24 log-spaced bands, half where it has just grown, silence as nothing), and matches them with dynamic time warping: once coarsely over the whole of both, then finely near that path. Either version may leave out up to half a minute at either end, so a lead-in, an intro or a tail that only one has does not drag the rest. The result is a list of time pairs, simplified to where the line bends, with a quality from how alike the matched spectra are; below 0.5 it is kept but not used. When an alignment is ready, every thread carried along it moves to where the same music is, unless someone placed it by hand, and comparison plays an aligned source at the matching moment rather than the same time. Nothing about the audio leaves the server: only the time pairs do.

## 032. Documents and pictures are shown only as pages the server drew

A PDF or a picture (JPEG, PNG, WebP, TIFF, BMP, GIF; never SVG, which can carry script) is drawn once, after upload, by the `document-render` job: Poppler for PDFs, ffmpeg for pictures, each page kept as WebP at 2000 pixels on its longest side and as a 320-pixel thumbnail, encrypted in storage like any other blob (`file_pages`). At most 300 pages of a document are drawn, and the viewer says when there are more. A reviewer asks for a document's pages and gets links bound to their session for a few hours, the same signed links that carry streams; every full page served is written to the access log as `page.render`, thumbnails are not. The original never reaches a browser this way. Region comments on pages and the per-viewer watermark burned into them follow.

## 033. Comments on a page point at a region, numbered in reading order

On a document or picture, dragging on the page with a mouse or pen draws a rectangle, and the next comment points at it: a `region` anchor in shares of the page's width and height, with the page number on a document. Without a drawing, a comment on a document points at the page shown (the whole page as a region, which reads as "P. 2"), and either can be switched to the whole file. The server refuses a page the document does not have. Open threads on part of a page are marked on it and numbered in the order the list reads (page by page, top to bottom), so a number on the page and in the list are the same thread; picking either picks both. A carried thread can be moved to a region drawn on the new version. On a touch screen a finger scrolls the page instead; drawing by touch follows.

## 034. The score sits beside the recording; bars are named, never synced

A track can link one PDF of its project as its score (`tracks.score_file_id`); the server refuses anything that is not a document. The recording's page then shows the score's pages, drawn and delivered like any document's, under the player, and links to the score's own page, where comments on it live. Recordings are not synced to their scores: in classical music, repeats, cuts, edits between takes and rubato make a bar map more trouble than help. Instead, in music projects only, a reviewer types the bars a comment is about ("25", "0" for an upbeat, or "9-12"); the comment keeps the moment of the recording they were listening to, so it plays from there, and reads "BAR 25" or "BARS 9–12". Other profiles have no bars, and the server refuses them there.

## 035. A recording has a QA view; the review screen stays with the music

A recording's file page has two views, kept in its address (`?view=qa`). Review is for listening and commenting: the player, the comments beside it, the score and Compare, with a single summary of what QA found ("−17.5 LUFS · 1 issue") that opens QA. QA holds what was measured: the quality checks, loudness and the meters, and the file's technical details. The player keeps its place in both, so switching views never stops playback. A guest has QA only when their review grants the meters.

The checks come in two kinds. Signal checks (clipping, flattened peaks, dropouts, clicks, DC offset, long silences, phase and mono fold-down) are measured once, in the same decode as the loudness analysis, and stored in `qa_findings`. Delivery checks (format, loudness, true peak, dead channels, balance) are read from those measurements against the project's delivery profile each time they are shown: Streaming, CD, Apple Digital Masters, broadcast (EBU R128), 5.1 surround or Dolby Atmos. A project without one is checked against the profile its channel count suggests, so changing profile needs no new analysis. Severity is shown by the dot's shape and fill, never by a traffic-light palette.

## 036. The prototype is the design contract

The clickable prototype in `apps/prototype`, approved in #105, is the design of the whole application: its navigation, layouts, copy, states, components and keyboard behaviour. `apps/web` builds what it shows; where building proves it wrong, the prototype changes in the same pull request. (Number 035 is held by the audio QA view in #103.)

## 037. Organisations are called workspaces

In every piece of copy (interface, email, documentation) the tenant is a **workspace**. The word "organisation" stays in code, the schema and the API (`organisation_id`, `organisationRole`, `/api/organisation`), so nothing is migrated. "Studio" was rejected because it reads as music-only.

## 038. Navigation: the sidebar carries the project, sections share one secondary list

Outside a project the sidebar holds Home, Inbox, Projects, what is waiting on you and recent items. Once a project is open, the sidebar shows a project switcher and the project's own navigation (Overview, Files, Board, Reviews, Tasks, People, Production, Settings), and the page header names the section; the project page has no tab row. Pages with sections (all settings, production) share one sticky secondary list at the left that holds its place on scroll. Tabs are kept for a third level. The player keeps its own layout. Members and workspace settings are reached from the account menu at the foot of the sidebar, not the sidebar itself. Home is a dashboard; the inbox is its own page with the bell's panel as its preview. A command palette (Ctrl or ⌘ K) replaces the search box, with a search page behind it. This supersedes the sidebar described in 028.

## 039. The instance is the same shell

Operators of an install work in the same application: the instance pages (overview, workspaces, operators, billing, support, health, queues, logs, debug tools, system information, settings, operations) appear as an Instance block in the sidebar, reached from the account menu or the fingerprint beside the bell, which is highlighted there. Operators are accounts with an instance role and always need a hardware security key. They never sign in as someone else. A workspace owner sees only their own workspace on the instance side.

## 040. Workflows are events, actions and connectors

A workflow is a graph of **nodes** and **connectors**. A node is an **event** (something happens: a version arrives, a decision is recorded, a due date passes) or an **action** (something is done: ask for an approval or feedback, assign a task, notify, set a status, wait, finish); each has named **outcomes**. A connector wires an outcome to a node and may carry a **condition**; a connector that runs back is a loop and needs a way out (an "until"). **Groups** frame a stage. The rules, checked by the builder and the engine alike: an action never starts a flow, an event never ends one, an action follows an outcome, a loop needs a stop, and nothing follows a finish. A project's workflows share one canvas; a basic view edits the same flows as a list of steps; every workflow can be read and written as YAML. This refines the stage model in `docs/domain.md` and #25.

## 041. Billing and support are modules, off by default

`HEKATE_BILLING` (off, stripe, paddle, manual) and `HEKATE_SUPPORT` (off; app, tickets in the application; link, an external desk; or mail, tickets sent to an address) are set in the environment and default to off, so a self-hosted install shows neither. `HEKATE_DOCS_URL` (default `https://docs.hekate.studio`) and `HEKATE_STATUS_URL` point the help menu at the documentation and a status page. With support on, the help menu offers the documentation, a workspace's tickets and a new ticket; a ticket's severity is limited by the workspace's plan.

## 042. Every visible error carries a reference

Any error a person can see (a 5xx, or a refusal worth a support question) carries a short reference such as `HK-7F3A-2C`, written to the structured log with the request, person, job and stack. Operators look references up in the debug tools; a ticket that quotes one links to it.

## 043. System information shows releases; the image stays immutable

The instance shows the running version and build, the update channel and the releases available with their notes and upgrade instructions. For 1.0, nothing is patched in place: an upgrade is a new image. Signed hot patches applied as overlays may come later as an explicit opt-in (#158).

## 044. Mail is plain text first, with an HTML alternative, and fetches nothing

Every message is one shape (who did what, one action, a line about why you got it) rendered from one structure into both parts of a multipart mail. The plain-text part is written as text: wrapped at 72 characters, links on their own lines, the foot after a `-- ` signature line; it is never derived from the HTML. The HTML part is laid out in tables, light colours inline and dark ones from a `prefers-color-scheme` query, and holds no images: the mark is drawn in table cells, so nothing is fetched and nothing reports that a message was opened. Every link goes to the app. A workspace may change each template's subject line, using only the placeholders that template offers. Mail about something a member is told of goes through the notifications table, which already retries; a message carrying a one-time link (a guest's link, an invitation) is sent at once and never queued, because job data holds no secrets, and the sender can send it again. Bounces are recorded once a provider that reports them is configured (#71).

## 045. One registry of keyboard shortcuts, and a map of what works here

What is on a page registers its shortcuts while it is there (`lib/shortcuts.tsx`), and one listener runs them; "?" opens a map of exactly those, grouped by where they belong. None fires while someone types in a field or while a dialog is open, Space and Enter stay with a focused control, and a change of state (playing, the loop, the sidebar, a comparison source) is announced to assistive technology. The player's keys work anywhere on its page, as in Frame.io: Space or K plays and pauses, J and L (or the arrows) jump by the chosen step, comma and full stop step a frame (a hundredth of a second for audio), I and O set the loop at the playhead and Shift+L turns it on or off; 1 to 4 pick a comparison source and C starts a comment at the playhead. Lists and the document viewer keep their keys to themselves when focused (j and k move a list) and show them on the map while they are on the page.

## 046. A second factor is asked for by the workspace, and owed before anything else

The first second factor is a code app (TOTP), because every phone already has one and it needs nothing from the instance; passkeys and hardware security keys join it (#39). A workspace requires it of nobody, of its owners and admins, or of everyone, and only someone who already has one can require it, so nobody locks themselves out; an instance can require it of every account. Someone who owes one is held at a single page that adds it (password, QR code and key, a first code, then the recovery codes) and every member route refuses them with a code the app acts on, rather than letting them work and asking later, because a requirement that can be put off protects nothing. Recovery codes are shown once and kept only as keyed hashes, like the guest links and reset codes, so a copy of the database signs no one in. A browser can be trusted for 30 days, as Linear and GitHub allow, so the second step is rare where people actually work.

## 047. A deleted account leaves what it did, as a former member's

Deleting an account keeps the record and removes the person. Comments, decisions and access log entries stay where they are, so a review's history and the log still make sense, but every one of them now reads "A former member": the account row stays only so that what was written keeps an author, and it holds no name, address, picture or preference afterwards. Sign-in, sessions, the second factor, memberships, project roles, preferences, notifications, follows, marks and saved searches go, and the address leaves every invitation that named it, in every workspace. An entry the log receives for the account after it is deleted (a request already under way) is labelled the same way by the database itself. Deleting needs a session but no workspace, so someone removed from their last one can still delete theirs. The access log stays append-only: the one change it allows is replacing the label on an account's own entries, in the transaction that deletes that account (migration 0040). Deleting needs the account's address typed out and its password, and is refused while the account is a workspace's only owner, as GitHub and Linear refuse it, so that no workspace is left with no one to run it. Words other people wrote about the person (a mention in a comment) are theirs and stay.

## 048. A session knows how it was signed in, and the rule reads the session

Each sign-in records its factor on the session: a password alone, a password and a second factor (a code, a recovery code, or a browser trusted after a code), or a passkey. A workspace's rule is then a rule about the session, not only the account: asking for a second factor is met by a code-backed or passkey session, and asking owners and admins for a hardware security key is met by a passkey session alone. An account that has a passkey but signed in with its password is not turned away; it is asked to confirm with the key (a step up, as GitHub asks for sudo mode), and only an account with no factor at all is asked to add one. Removing a code app takes what it gave from the session at once. Passkeys and hardware security keys are both WebAuthn credentials: a synced passkey and a single-device key are listed as such, each named, with when it was last used, and an account may hold up to five unless the operator raises the limit (`MAX_PASSKEYS`).

## 049. A directory signs people in to its own workspace, and never takes over an account

LDAP and Active Directory are set per workspace rather than per instance, because one instance may serve several organisations with their own directories, and a directory is trusted only about its own people. Someone signs in by naming the workspace, then their directory username and password; the directory checks the password, never Hekate. Their first sign-in makes the account and the membership, as single sign-on does in Linear and Slack, and each sign-in sets the role their groups give, so leaving a group takes effect at the next sign-in. A directory can make admins and members, never owners: owners are made by people. An address that already has an account here, made by invitation or another directory, is refused rather than linked, because linking on an address alone would let whoever controls one directory sign in as anyone. The sign-in page only offers a directory while some workspace has one turned on, and says no more than that. The first sign-in makes the account, its link to the directory and the membership in one transaction, one sign-in per address at a time, so two at once make one account and a failure part-way leaves nothing behind. An account made this way has no password here: deleting it is confirmed with the directory password, checked by binding as the person it is linked to.

## 050. Single sign-on is found by workspace, links no one, and owners keep a way in

Each workspace may have one identity provider, by OIDC or SAML, on Better Auth's SSO plugin; Hekate keeps the settings and writes the configuration the plugin reads, and turns off the plugin's own routes for registering providers, so only a workspace's admins set one. Someone signing in names the workspace, as in Slack and Linear, rather than having their address's domain pick a provider, because any workspace could claim a domain. A provider vouches only for the people it brings: an address that already has an account is refused, never linked, for the same reason as a directory (decision 049). Groups make admins and members, never owners. Once anyone has signed in through a provider it cannot be swapped for another (a new protocol, issuer or entity ID), because an account is known by its provider and its subject there, and another provider's subjects are other people; its other settings still change. Addresses the server fetches are checked at the connection itself, against every range that is not the public internet, so a name cannot resolve one way for the check and another for the request. Enforcing single sign-on refuses members whose session came another way, at every member route and play link, but never owners, so a misconfigured or unreachable provider cannot lock a workspace out (break-glass, as GitHub and Linear keep for owners). An account made by single sign-on has no password here, so deleting it is confirmed by signing in again: a sign-in in the last ten minutes, with the address typed out, confirms it, as GitHub's sudo mode does; the same holds for an account that signs in with a passkey alone. The tests run against a real Keycloak, for both protocols, locally and in CI.

## 051. Rate limits live in PostgreSQL

Every rate limit (Better Auth's for sign-in and codes, and Hekate's for guest links, uploads and content keys) is counted in PostgreSQL, in one statement per request, rather than in the memory of one process. A limit kept in memory is only a limit per replica: with three replicas, an attacker gets three times the tries, and a restart forgets them all. The database is already the one thing every replica shares, so no Redis is added; a fixed window per key is enough at these volumes, and an hourly job removes counts older than a day.

## 052. Comments leave as each editing system's own marker list, written once in shared code

A file's comments export as the marker list each application already imports, not one generic file people must convert: a marker EDL for DaVinci Resolve, FCPXML to-do markers for Final Cut Pro, Final Cut 7 XML for Premiere Pro, Media Composer's marker text, Reaper's region and marker list, a CSV for Nuendo's marker import, and a MIDI file of markers for Pro Tools. Pyramix, SADiE and Sequoia publish no marker import we could check against, so they are left out until a marker list exported from each shows what to write (#233). The writers are pure functions in `packages/shared`, so the dialog's preview is the file itself and the server's download is the same bytes. Exporting needs the triage permission, because it carries feedback into an edit, and each export is in the access log. Threads hidden on a version stay out; threads without a time stay out of marker lists and are counted, and CSV and plain text keep them.

## 053. A review's activity is read from the access log, and shows names only

The review page's activity (who asked, reminded, moved the date, added or removed whom, who was sent a link and opened it, and who cancelled) is read from the access log, which already records every one of those actions with the review it belongs to, rather than from a second log kept beside it. Decisions and feedback come from their own records, which hold the notes. The page shows names alone: the addresses, network addresses and agents the access log keeps stay there, for the people who may read it. Guests see no activity, as the prototype shows. Reminders are on demand as well as the day before a review is due, at most five to a review an hour, and changing the due date lets the day-before reminder go out again. Moving items on to a workflow's next stage waits for workflows; until then the gate shows whether the review passed.

## 054. A version is checked before it lands, and a producer can let it through on the record

A project can ask that a new version pass checks before it becomes the next version (#131): that its audio's true peak is under the delivery profile's ceiling, and that it comes with an edit decision list. Both are off unless the project turns them on. A refusal is a real answer from the server (422, `version_refused`) whose message says what failed and by how much; a file still being measured is answered with 409 (`version_measuring`), to try again shortly. Whoever may edit the project's workflows can let a refused version through: the version records who did, and the access log has a `version.let_through` event naming the checks it passed by. Until workflows exist, these are the upload workflow's checks; they become its first stage when they do. Whoever adds a version also confirms or corrects what decision 029 carries over: each of the previous version's open threads is carried and shown (the default), carried but hidden, or settled as fixed or won't fix as the version lands. Replacing a version's file with a corrected export of the same kind moves its threads, carried threads and alignments to the new file, keeping every comment, and is logged as `variation.replace`.

## 055. Categories belong to the project, deferral waits for a stage by name, and triage sends lists

Comment categories are rows of the project (#36), seeded with the prototype's five when the project is made (or, for a project made before them, the first time they are read, under a lock on the project row so two first reads make one set). Each carries its handling: normal, deferred to a named stage, or information only. Giving a comment a deferring category defers it to that stage unless triage says otherwise; changing it to one that does not defer brings it back. Workflows do not exist yet, so a deferred comment holds the stage's name, not a reference to it, and comes back when someone undefers it; when workflows give stages ids, the names are matched once and starting a stage brings its comments back. Assignment names a member of the project, and the triage view's last step sends each person the open comments assigned to them on that file as one notification, by mail too unless they turned it off ("assigned"), rather than a message per comment. Triage acts on up to two hundred threads at once, in one transaction, under the same lock as carrying threads to a new version, so a version being made never sees half a triage. Guests never see who a comment is assigned to.

## 056. A download is made for one person, through a link that works once

Downloading has three levels: none, the proxy, or the original (which allows the proxy too). A project role gives a level through two permissions, "Download proxies" and "Download originals", which the Producer, Engineer and Editor roles have and the Reviewer and Viewer roles do not. A review gives each guest a level of its own, none unless it says otherwise; a guest in several reviews has the widest. Asking for a download returns a link, never the file: the link works once, for five minutes, in the session that asked for it (another sign-in of the same account cannot use it, and does not spend it). Opening it checks the permission again, writes the download to the access log, and only then sends the first byte, with nothing allowed to cache it. People may ask for twenty downloads an hour. What is made depends on the file: a recording's original as it was uploaded (audio carries no mark until #32) or its stream's AAC encode, decrypted segment by segment into one MP4; a picture as it was reviewed, with the recipient's name drawn across it. Video, documents and pictures' originals follow, with their marks, as a rendering job. Links nobody opened are removed a day later.

## 057. A review shows each guest what it names: items, versions, tools and plays

Each guest's grant in a review now also says which of the review's items they see (all, unless it names some, and never none), whether they see a track's earlier versions as well as the one under review (not unless it says so), and how many times they may start playing each file (without limit unless it says so). QA is a tool of its own rather than part of the meters, and the score is one too: with it, a guest sees the track's linked score beside the recording. All of it is enforced by the server, in what a guest can reach at all, so a file outside their grant does not exist for them. A play is a playback session started, counted per guest and file and recorded with its access log entry under one lock, so two starts at once cannot both pass the last allowed play; a session lasts four hours, so a long listen is one play. Grants made before these fields read as their defaults, and a migration gives QA to every grant that had the meters, so nobody loses what they could see. Comparing versions, inviting others, and per-project defaults for reviewers follow (#55).

## 058. A role is a level in each area, kept as the permissions it stands for

A project role is chosen as one level in each of nine areas (files, comments, reviews, downloads, sessions and takes, production tools, workflow, roles and people, the project itself), as the prototype's Roles and access matrix shows (#142), rather than as a list of separate permissions. A level includes those before it, so nobody can be given, say, deletion without seeing the files. Underneath, a role is still the set of permissions its levels grant, stored as before, and every route still asks for one permission: the levels are how people choose and read a role, and the permissions are what the server checks. A role from the API may be sent either way, and whichever is sent is normalised to whole levels. New permissions made the levels complete: reading comments, deleting files and folders, seeing and editing takes and the production tools, seeing the workflow and the people, and editing or archiving the project. A migration gives existing roles the new ones their old permissions implied (seeing comments, takes, the workflow and the people to whoever could view; deleting to whoever could organise; the project's settings and archiving to whoever managed roles), so nobody loses what they could do. The last role able to manage people keeps that level, and cannot be deleted. Those whose work is choosing among the people (requesting a review, assigning feedback) can look them up whatever their People level. An archived project keeps each role's looking permissions (files, comments, takes, production, the workflow and the people) and nothing more. Guests have no role: they read the comments their review lets them see. The project's settings are one page per section, as in the prototype: General (name, profile, description, archiving), Comments (categories, carry-over), Roles and access, Workflow (the checks on a new version) and Delivery profile; each control is live for whoever holds the permission it needs and read-only for the others, and the page is offered to whoever may change something on it. Asset security, storage, QA rules, the player tools per role, templates and deleting a project follow with the features behind them.

## 059. A file is measured against the nearest profile, and a workspace's own profiles are shared

What a recording is measured against is chosen at four levels (#144): the file itself, its track, its project and the workspace. The nearest choice applies; without any, the profile its channels suggest, as before. A track's choice reaches the files of its versions' variations. The choice is resolved by one pure function in `packages/shared`, `effectiveProfile`, which the QA page, the project's failing checks and the version checks all call, so they can never disagree. A workspace can add its own profiles beside the built-in ones (a loudness target and tolerance or none, a true peak ceiling, sample rates, a bit depth and a layout, any layout included); every project in it can choose them, and they are referred to as `custom:` and an id wherever a built-in one is named by its id. Only workspace admins make, change and remove them, since every project shares them; choosing one for a project, track or file needs that project's workflow level, as choosing a built-in one does. Removing a profile removes every choice of it in the same transaction, so what chose it falls back to the next level up rather than to a name that no longer exists; a reference that is somehow missing is passed over the same way. Delivery findings are still read from the stored measurements whenever they are shown, so a new choice needs no new analysis. The QA rules by category, with custom rules, follow in #144's second part.

## 060. A project's QA rules are read against stored measurements, and its own rules are plain comparisons

A project chooses how its checks bite (#144): the signal checks (clipping, flattened peaks, dropouts, clicks, DC offset, silence, phase) always run, and only their severity moves; the delivery checks (format, loudness, true peak, dead channels and balance) are one switch together and can each be turned off; and the project can add rules of its own. Like the delivery checks (decision 059), all of it is applied when a report is read, from the measurements stored at analysis, by pure functions in `packages/shared` (`applyQaSettings`, `ruleFindings`), so a change shows in every report at once and needs no new analysis. A rule of the project's own compares one measure (sample rate, bit depth, channels, duration, integrated loudness, true peak, loudness range, codec or file name) with a value: is, is not, at least, at most, between, one of, or, for names and codecs, a wildcard pattern. Patterns take `*` and `?` only and are matched whole, never as a regular expression, so a rule cannot be made to run away on a long name. The rules are stored as one validated JSON value on the project, edited by whoever edits its workflow, and a template carries them. Rules for video and artwork, and running rules as a file arrives (warning or refusing at upload), follow with the checks and the workflows they need.

## 061. The installer runs in the server before it is configured, behind a code from its log

A clean install is configured in the browser (#127), as the prototype's installer shows: requirements, database, storage, the master key, mail, the public address, then the first workspace and its owner. The server starts in an install mode whenever it has no database or no master key, or when the settings file it wrote is not yet marked finished; in that mode it serves the web app and the installer's routes and nothing else. Anyone who reaches a fresh instance could otherwise claim it, so every installer route, and creating the first owner, asks for a setup code that the server prints in its log at start (`docker compose logs app`), as Jenkins and Grafana do; wrong codes are counted and refused after ten in ten minutes. What the installer is given goes into a settings file (`HEKATE_SETTINGS_FILE`, `/config/hekate.env` in the image, on a volume of its own so a copy of the media never carries the master key), written atomically and readable by the server alone; it is read at every start, and the environment wins over it, so anything set in Compose or `.env` is shown as fixed and never overwritten. Each step is tested before it is saved: the database is reached and migrated, the storage is written to and read back, the mail settings send a test message, and the address is looked up and asked for a nonce only this server knows. Mail is SMTP, with the hosts and ports of the common providers filled in. When the last step is saved, the settings are checked as a whole, the file is marked finished, and the full server starts in the same process, so no restart is needed; the first workspace and its owner are then created as before, behind the same code. Workspaces on their own subdomains are left out until the server can serve them.

## 062. Operators are accounts with a key, and an owner sees only their own workspace on the instance side

The instance side (#155) is reached in the same shell, from the fingerprint beside the bell or the account menu, by two kinds of people, and the server decides which on every request. Operators are ordinary accounts listed in a global `instance_operators` table (no workspace owns it, since an operator acts across all of them); the installer's owner is the first, an existing instance's earliest owner becomes one when it upgrades, and an operator makes another by their address. An operator acts only from a session signed in with a passkey or hardware security key (`OPERATOR_SECURITY_KEY`, on by default), so a stolen password alone never reaches every workspace; signed in another way they are shown how to sign in again with their key. The last operator cannot be removed. A workspace's owner who does not operate the instance sees their own workspaces there and nothing else, and only those whose sign-in rules their session meets. Everything an operator does is written to a global `instance_events` table, which the Overview lists and the audit tables (#157) will read. The Overview counts workspaces, people, storage and the job queue, and lists what needs an operator: jobs that failed today, files missing from storage, and operators without a key. A workspace's own tabs, creating and suspending workspaces, follow in #174.

## 063. A suspended workspace keeps everything and lets nobody in, and operators help members without becoming them

An operator suspends a workspace with a reason (#174), held on the workspace's own record. `requireOrganisation`, the member and guest viewer, and playback all refuse it with `workspace_suspended` and that reason, except where a member reads who they are and switches to another of their workspaces; they are shown a notice saying why, with their other workspaces and a way to sign out. Its guests' sessions end and their links do not open, giving the same answer as a link that no longer works. Nothing is deleted, and reinstating lets everyone back in as they were. The instance side itself stays open, so an operator whose own workspace is suspended can still reinstate it. A new workspace is made with a name, a subdomain and its first owner's address, who is invited as any member would be, so no account is made for anyone. The list pages by name and id rather than by offset, so a workspace made or suspended while someone scrolls does not shift the pages. Reading a workspace's members, projects and recent activity names the workspace in the path; that is deliberate here alone, since the instance side spans workspaces, and every such query is still scoped with `inOrg` to that one. Operators never sign in as a member: for someone locked out they can send a password reset, remove their code app and passkeys so they enrol again, or end their sessions, and each is written to the instance's events. The storage, billing, settings and keys tabs, and deleting a workspace after a grace period, follow.

## 064. A workspace is deleted thirty days after an operator asks, and its key is rotated by rewrapping, never re-encrypting

Only a suspended workspace can be deleted (#174), and it is purged thirty days later (`WORKSPACE_DELETE_GRACE_DAYS`) by an hourly job. Until then nothing is lost: reinstating it, or keeping it, clears the date. The purge deletes the workspace's rows in one transaction (the access log among them, under the explicit purge the log allows, and variations before the cascade reaches their files), then every object under its prefix in every storage backend. If a backend fails part-way, what is left is an orphan, which the storage reconciliation reports and removes. The purge is written to the instance's events, which outlive the workspace. Rotating a workspace's key makes a new version that everything new is wrapped with; a background job then rewraps every blob's data key, every rendition key, every upload in progress and the directory's bind password with it, a batch at a time and only where nothing changed the row meanwhile. The stored bytes are never re-encrypted, and earlier versions are kept, so a backup taken before the rotation still opens. The Storage, Settings and Keys tabs show the workspace's bytes by backend and what reconciliation found, the settings its owner chose (read-only to operators), and its key's versions with what an earlier one still wraps. The Billing tab says the instance does not charge until billing is set up (#180), and quotas follow with #175.

## 065. Every failure has a reference, kept for thirty days, that operators look up

A failure a person can see carries a reference (#159): `HK-`, four hexadecimal digits and two, short enough to read aloud and paste into a message, unique among the reports kept. Any 5xx from the API, whatever threw it, and a job's last failed attempt (not the attempts that will be retried) are recorded in a global `error_reports` table, since a failure need not belong to any workspace, and written to the log as one JSON line with the same fields. The API returns the reference beside its message, and the web app adds "Quote HK-… to support." to the message every page already shows, so no screen needs its own handling. Refusals (4xx) say what was refused and carry no reference. A report keeps the route or the job's name, the server's own request id (sent back as `X-Request-Id`), the error and its stack, the job's data, the workspace and the account; operators see the account as its name and email, nothing more. Recording never throws, and a workspace or account that has gone is left off rather than losing the report. Reports go with their workspace and after 30 days (`ERROR_REPORT_DAYS`), in the hourly purge. Debug tools looks up a reference however it is pasted and lists what failed in the last day by the viewer's clock. Inspecting a file, a review or a session, replaying webhook deliveries and feature flags follow in #159's second part; workflow runs and webhooks are not built yet, and a ticket (#181) will attach a reference when it is built.

## 066. Operators inspect a file, a review or a session read-only, and every look is recorded

Debug tools' inspectors (#159) open a file, a review or a session by its id, or by a link pasted from the address bar, for an operator working out why something does not work. A file shows its rows, where its bytes are stored and with which key version, its renditions and drawn pages, every job in the queue whose data names it, its error reports and its access log by action. A review shows its items and reviewers, what each reviewer was allowed, what they opened and when, a guest's sessions, and its access log. A session, a member's sign-in or a guest's, shows who, its workspace, when it began, was last used and ends, how it was signed in, where from, and what the access log holds for them since it began. Nothing can be changed from them, and no stored content is shown: names, sizes and ids only, never a file's bytes, a comment or a key. Each inspector first finds which workspace holds the row, the one read across workspaces, which the instance side alone may make; every read after it is scoped to that workspace with `inOrg`. Every look is written to the instance's events as the operator's, naming the workspace, so a workspace's owner can be told who looked and when. Replaying webhook deliveries and inspecting workflow runs wait for webhooks and workflows; feature flags and running the QA checks on a file follow.

## 067. Mentions are chosen, not guessed, and a thread can be a task

A comment's mentions (#133) are chosen in a picker that opens when `@` is typed (or from **@ Mention**) and lists the project's people by name, never by address. The comment carries their ids beside its text, and the server refuses any that are not members who can see the project, so nobody outside it is mentioned or told; a guest is offered nobody and cannot choose anyone, since the project's people are not theirs to see. The names are kept as they were written, so the text and its highlighting still agree after someone is renamed. Names typed without the picker, a guest's among them, are still read from the text and those people told, as before, but they are not shown as mentions. An edit that adds a mention tells only whoever is new to it. Triage can make a thread a task, shown as *to do* until it is *done*; whoever it is assigned to may mark it done or not done without triage, and nothing more. Tasks and assignees stay from guests, as triage does. A thread's history now says where its anchor was moved by hand. Attachments, and takes attached to a thread with the compare they open, follow in #133's later parts.

## 068. Flags are read as the server runs, and a failed job runs again from its report

Debug tools' flags (#159) are switches an operator turns for the whole instance, kept in a global `instance_flags` table and listed in `packages/shared` (`instanceFlags`), each one something the server does today. Every process reads them at start-up and again every fifteen seconds, so turning one needs no restart and reaches every worker; one that cannot be read is off. A flag may last a set time and then go off by itself: the first, verbose logging for the worker, writes every job's start, end and time to the log for an hour. Turning one is an instance event. A failure from a job can be run again from its report: a file's preparation by the same plan a member's retry uses (what failed waits again, and its jobs are queued), any other job with the data it had, checked against its schema; a request's failure has no job to run. Running the QA checks on a file again is left out, since the checks are applied whenever a report is read (decision 060), and the prototype drops it. Replaying webhook deliveries and inspecting workflow runs wait for webhooks and workflows.

## 069. A comment's attachments are encrypted, and reach a browser only as a one-time download

A comment's author can attach up to five files of 25 MB each to it (#133): a photo of a marked-up part, a PDF of bowings, a reference recording. Each is stored as an encrypted blob like any other file's bytes and listed with the comment by name, type and size only. Its bytes reach a browser only through a download made for the person asking: a one-time link in their session, for five minutes, on the same tickets as a file's downloads (decision 056), with the comment checked again as the link is made and as it is used against the threads the file shows that person, so a guest reaches only what their review's comment scope lets them see. Downloads and additions are in the access log. Attachments are not watermarked, since they are the reviewers' own material rather than the media under review, and they are never shown inline, so nothing a reviewer attaches runs in the page. Only the author removes an attachment; it goes with its comment and its workspace, and storage reconciliation counts its bytes as in use. Takes attached to a thread, and the compare they open, follow with take coverage (#46).

## 070. A take belongs to its track, sessions record tracks, and bars are optional

Takes hang from tracks, not from sessions (#21): a track has many takes, numbered in the order they are added, and a session is linked to the tracks it recorded, many to many, since a track is often recorded across several days and a day records several tracks. A take is one file for now, its scratch mix, which is any audio or video file already in the project (or uploaded into the track's folder from the take manager) and not a version's; uploading one file per microphone follows. Its rating (out of five), star, notes and label are the producer's, and its score page, bar range and in and out points are all optional, because bars matter for a classical piece and rarely for a pop song. A take with bars is found by them: asking a track for the takes covering a bar lists the starred ones first, then by rating, then in order, from one pure function in `packages/shared` (`takesCovering`), which the coverage view and "Other takes for bar N" on a bar comment (#46's second part) will also call. Seeing takes needs the project's takes level of View, changing them Edit; a file that is a take says so in its details only to those who can see takes. No version of Hekate could make a take before this, so the migration removes any rows the old shape held rather than guessing a track for them. Sessions' own pages, importing takes with their metadata (#45), matching takes to tracks by their audio, and reading an edit map from the editor's project follow.

## 071. A thread on a bar lists the takes covering it, and the takes view marks what none covers

"Any other options for bar 72?" is answered where it is asked (#46): a thread anchored to bars on a track's version offers **Other takes**, which lists every take of that track covering the thread's first bar, starred first, then by rating, then in order, from the same `takesCovering` the track's takes view uses. It is offered only to members whose role lets them see takes; a guest reviewer never sees it, and will hear only the takes shared with them on a thread when sharing is built (#133). The takes view marks the bars no take covers under its ruler and names them ("no take of bars 17 to 24"), from `coverageGaps`, counting from bar 1 to the last bar any take reaches. Auditioning a take at the bar, looped and level-matched, and which take the current version uses, wait for the audition player and the edit decisions (#56).

## 072. Takes are shared on a thread, and a guest hears only those

A producer answers "any other options for bar 72?" on the thread itself (#133): from **Other takes**, whoever triages the file, and may see takes, ticks the takes to share, or shares every take covering the bar, or all but the ticked. Shared takes hang from the thread's first comment and show on it as "2 takes attached", opening their list; each opens in the player. Everyone who sees the thread hears them, which is the point for a reviewer with no take access of their own, such as a conductor reviewing as a guest. A guest's reach is widened by exactly those takes, through a thread their review shows them, and only to listen, within the window and play limit of the review that shows the thread (docs/security.md). Sharing and unsharing are in the access log, and unsharing closes the take to the guest at once. Flipping between the version and the shared takes level-matched at the bar, as the prototype's compare shows, waits for the audition player.

## 073. A project template is a saved copy of a project's set-up

"Save as a template" (#240) copies a project's roles, comment categories, delivery profile, QA rules and version checks into a workspace template, stored as one value validated by `templateContent` in `packages/shared`. It is a copy, not a link: changing the project afterwards leaves the template as it was, and the project may be archived or deleted without it. Files, people, reviews and comments never go into one. Saving needs the project's edit level; every member sees the workspace's templates and may start a project from one, as they may start one from any project they can see, which now also copies that project's categories. Whoever saved a template, or a workspace admin, may remove it. A template naming a workspace profile that has since been removed starts its project on the workspace's default instead. Tool access per role joins templates when it is built.

## 074. Each project role has its player tools, and the server refuses the engineer's ones

A project's roles each have the player tools on or off (#240): QA, meters, the spectrogram, the score, compare and loops, in a matrix under Roles and access beside the access levels. A new project's Producer, Engineer and Editor have them all, a Reviewer the score, compare and loops, and a Viewer the score, as the prototype's conductor sees no QA; a role made later listens (score, compare, loops) unless it says otherwise, and roles made before this keep every tool, so no project changes by itself. Workspace owners and admins have every tool whatever their role. QA, meters and the spectrogram are refused by the server to a member whose role has them off, as they are to a guest whose review leaves them out (decision 060, #55), through one check, `mayUseTool`; the score, compare and loops are interface, hidden only. A role's tools go with it into a template and into a project started from another. Normalised playback joins the list when it is built; exceptions for one person or group follow.

## 075. A project chooses the references a comment may name

Pages, bars and beats are references a reviewer types beside a comment as they read it from the score (#240), never derived from the time and never on the scrub bar. A project switches each on or off under Comments, References; until it chooses, a music project takes all three and a video or general project none, so no project changes by itself, and a video project may now take bars (a score-cued film, a musical). The choice is stored on the project as one value, `comment_references`, validated by `commentReferences` in `packages/shared`, and travels into templates and projects started from another. The server refuses a bar anchor the project does not take, with the reason, through `referenceProblem`; the bar anchor gains an optional `page`. In the composer a recording has Page, Bar and Beat fields; on a document the page is the one shown. Changing them needs the project's edit level.

A track may choose its own references over its project's, under Comments, Overrides, from the sets that make sense (none; bars; bars and beats; pages and bars; pages, bars and beats), or keep the project's. The choice is `tracks.comment_references`, null for the project's, and applies to the variations of its versions and to the score it follows; a score several tracks follow takes the first one's. Choosing needs the project's edit level, as the project's own references do. It stays with the track, so templates do not carry it.

## 076. Normalised playback turns a recording down to its delivery target, and never up

A project chooses normalised playback (#240) under Comments, Versions: off, the default, so no project changes by itself; each person's choice; or always. Where it is a choice, the player's View menu offers it to a role with the new Normalise tool, which every listening role has (a new project's Viewer does not, and the migration gives it to existing roles that already compare); a guest's review has no such tool, so a guest hears it only when it is always on. The server works out the volume, the delivery profile's loudness target over the file's integrated loudness, and sends only that and the target in the file's payload: the measurements themselves stay behind the meters tool. The volume only ever turns down, as comparison's level matching does, because a media element cannot play above full volume and turning a quiet recording up would clip it; a recording under its target plays as it is. A file with no audio, not yet measured, or whose profile names no loudness target plays as it is. While comparison is shown it sets the volume itself, its sources matched to one another, and the page's volume returns when it closes. The choice is remembered per browser, and goes with the project into templates and projects started from it.

## 077. Deleting a project takes two people and seven days

Deleting a project (#240) is asked for by someone whose role may delete it, and confirmed by a workspace owner other than them, who types the project's name, as the prototype shows. A workspace with one owner has no second one to ask, so its owner confirms their own request, but only a day after asking: a deletion is never one moment's decision. The other owners are told in the app and by mail (a new notification, on by default). Confirmed, the project is archived at once, its open reviews closing, and goes for good seven days later; until then anyone who could withdraw the request (whoever asked, or anyone whose role may delete the project) can keep it, and it cannot be unarchived while it is due. The scheduled purge then deletes its rows in one transaction, discarding unfinished uploads first, and its stored bytes go at the next storage reconciliation, as a deleted file's do. Asking, confirming, keeping and the deletion itself are in the access log, which keeps the project's id and name after it has gone. Transferring a project waits for a decision on what it means (#240).

## 078. A project may keep its new files on a backend of its own

A project may choose the storage backend for its new files (#240), over the workspace's choice (decision 017) and the instance default, under Protection, Storage, as the prototype shows. ## 079. A project chooses whom its visible watermark marks, where and how strongly

The visible watermark (#31, docs/security.md) is a project setting under Protection, Asset security: whom it marks (off, guests only, or everyone), where (tiled, the bottom right corner, or the centre) and how strongly (an opacity from 10 to 80 per cent), with a preview in the viewer's own name. Until a project chooses, it marks guests only, tiled and faint, as before. Downloads are always marked for the person who asked, whatever the project chooses (decision 056). The choice goes into templates and projects started from another, and is the project's edit level's to change.

## 080. Documents and picture originals download as marked pictures

A download is always marked for the person who asked (decision 056), so a document or picture can only leave as something the mark is drawn on (#136). A picture's original is the stored picture at full size with the mark burned in, written back as JPEG, PNG, WebP or TIFF to match it (other formats become PNG); ffmpeg reads it with the single-picture demuxers only, as when its pages are drawn. A document leaves as a PDF: its proxy is the pages reviewers saw, each marked; its original is each page drawn again from the original PDF by Poppler at 300 dots an inch (less for a page so large that its long side would pass 4,200 pixels), marked, at the page's own size. The PDF is written by Hekate itself, one JPEG a page and nothing else, and sent as each page is made, so a long score starts at once and never sits whole in memory; the work happens in a private workspace that is removed when the download ends or the browser stops it. The first page is made before the response starts, so a document that cannot be marked is an error rather than a broken file. Text in the original stays behind: a marked page is a picture, which is the point. A document that is not a PDF and has no pages has nothing to mark and so nothing to download, as does a page beyond the 300 that are drawn. Invisible marks in PDFs follow with forensic marking (#32); video follows in decision 081.

## 081. A video download has the mark burned into its picture as it is sent

A video downloads with the recipient's mark burned into every frame (#136), encoded as it is sent rather than by a queued job: the download starts at once, nothing marked is ever stored, and the browser's progress is the encode's. Reading slowly slows ffmpeg rather than filling memory, and a download stopped early stops it and clears its private workspace. The proxy is the largest stream encode, decrypted and encoded again with the mark at the stream's quality, as MP4. The original is the original at its own size, encoded again in H.264 at a quality meant to be worked from (CRF 16), as QuickTime; its sound is carried as it was where QuickTime can carry it (PCM, AAC, ALAC, MP3, AC-3, E-AC-3) and as 24-bit PCM otherwise, judged stream by stream, and every audio stream goes with it. A mark burned in cannot leave the picture untouched, so an original video is never the original bytes: the dialog says it is encoded again. The source's own metadata (places, devices, names) is left out. Odd frame sizes lose their last line, as 4:2:0 H.264 needs. Both are opened as any upload is, with files only and real media demuxers only. Like every media tool, the encode has a deadline: ten times the film's length, never under a quarter of an hour, after which it is stopped, so neither a stalled tool nor a stalled reader holds it; the copy of the source into the workspace stops too when the browser goes. Forensic marks, which survive re-encoding, follow with #32.

## 082. A review may give compare and inviting, and a reviewer invites as a guest

Each invitation is an email, so a reviewer may send ten an hour; each is in the access log as the inviter's, naming who invited them. Off by default, as are grants made before it existed. Managers of reviewers add people as before, with the review's grant.

## 083. Comparing two versions: aligned by their audio, the checks fixed and new, blind on request

A track's versions can be compared two at a time on a page of their own (#137), reached from the track page's Compare and from a version's "Compare with the previous version", as the prototype shows; it is a member's tool, as compare is. The earlier version's open comments show where they fall in the other once the alignment is good enough to follow, and not before.

## 087. Prometheus reads Hekate's metrics at /metrics, with a token

Hekate exports its metrics in Prometheus's text format at `/metrics` (#70), as the prototype's catalogue lists them, and only when `METRICS_TOKEN` is set: a scraper sends it as a bearer token, compared in constant time, and without it there is no endpoint at all. ## 090. A QA report to take away, as PDF, CSV or JSON

The QA view offers the report to take away (#43), as the prototype's dialog does: PDF to read and send, CSV for a spreadsheet, JSON for another program. ## 091. Two more audio checks: whether a file decodes whole, and how high it reaches

The audio QA gains two signal checks (#41), both measured when a file is analysed. **Integrity**: a file that decodes to less than the length its header declares (by more than half a second, or one per cent of a long file) fails, marked where the audio stops, and so does one the decoder reported errors in on the way through; otherwise it passes. **Bandwidth** reads the spectrograms the analysis already makes, so it costs no second decode: the spectrum averaged over every column that is not silent, the loudest channel band by band, judged against the music's own level between 1 and 5 kHz. A sharp wall (a fall of 30 dB within a few hundred hertz, with nothing after it) between 10 and 20 kHz is worth a look, as a lossy encode leaves it; so is a wall around 20 to 24 kHz in a file of 88.2 kHz or more, which was most likely made at 44.1 or 48 kHz and converted up. Music that fades into its noise passes however early it fades, and a recording with nothing between 1 and 5 kHz to judge against (a test tone, a bass line alone) is not judged. Both are signal checks, so a project can change their severity as it can the others'. Files analysed before these checks have neither until they are analysed again.

## 092. The QA view says what was fixed and what is new since the version before

## 093. What a recording says about itself is read when it is probed

A recording's embedded metadata is read when the file is probed (#41) and kept with its media information: Broadcast Wave's bext chunk (description, originator and its reference, origination date and time, time reference, coding history) and iXML (its size, and project, scene, take, tape, note and timecode rate), read from the file itself, chunk by chunk without touching the audio, as ffprobe folds bext into other tags and skips iXML; RIFF, RF64 and BW64 are all read. The common tags of ID3, Vorbis comments, MP4 and RIFF INFO (title, artist, album, album artist, composer, genre, date, ISRC, copyright) come from ffprobe by whatever name the container gives them, and embedded artwork by its codec and size. Each value is kept to 500 characters; metadata never stops a probe. The QA view lists it under the file's details, as the prototype's Embedded metadata panel does, with ISRC and artwork always shown (as "none" where missing) because deliveries ask for them; the PDF report lists the same, and the JSON report carries it whole. A project's own rules can ask for ISRC, title, artist or the bext originator; a field the file lacks reads as empty, so "matches ?*" asks for one to be filled in, and a file whose metadata was never read is not judged on it. Files probed before this have none until they are probed again. Editing metadata (the prototype's Edit) follows separately; ADM is read as decision 096 says.

## 094. Each viewer places a file's comments: beside the player, below it, or away

## 095. A share is a review that asks nothing

Sharing outside a review (#138) uses the review system with a third kind, `share`: the same items, people (members, guests and groups), guest links, per-person permissions and access log, and nothing asked. A share's people never comment, decide or invite others, whatever the workspace's defaults, an override or a later change says; they only listen and look, and download where it says so. It has no rule, order, due date or reminders, and never settles: it runs until it is stopped ("Stop sharing", the review's cancel). Nothing waits on its people, so it is never anyone's turn, never in the inbox's asks and never puts a track in review. They are told with words of their own ("shared … with you", a mail template of its own): how long it is theirs, how often they may play each file, what they may download. Those who run it see, for each person, when they first opened it and how often they played and downloaded what it shares, from the access log: a guest's plays and downloads carry the share; a member's carry only the file, so theirs are the shared files' since it was shared, until it ended. The prototype's "A link" (anyone with the link, after giving an email) is a separate feature and follows later.

## 096. Channel layouts, ADM masters, the LFE and Atmos are checked

A recording's channel layout is named as engineers name it (#74), main channels, LFE, then height ("5.1", "7.1.4"), from the layout ffmpeg reports (which follows a wave file's channel mask), or, for an ADM master, from its bed. An ADM BWF master is read when it is probed, from its chna chunk (which track plays which channel format) and its axml (the speakers a renderer names for its own channel formats, and the programme's name): its DirectSpeakers tracks are the bed, named from ITU-R BS.2094's common definitions or from the speaker labels (ITU's, and the renderer's own such as `RC_Ltf`), and its Objects tracks the objects. A bed with a channel neither describes is counted but not named. A `dbmd` chunk marks Dolby's own metadata, which its renderer writes. Hekate decodes no Dolby-licensed format, as settled on #74; an ADM master's channels are analysed as recorded.

Three checks follow. **Layout**, a delivery check, compares the file's layout with the profile's, where the profile names one and the channel count is already right: a different layout fails, and a file that does not say how its channels are laid out is worth a look. **Atmos**, a delivery check, asks a profile that wants ADM (the built-in Dolby Atmos, now "Dolby Atmos (ADM BWF)", which takes any number of channels) for an ADM master: none fails, ADM without Dolby's metadata is worth a look, and an ADM master measured against a profile that does not want one gets a note. A file probed before ADM was read is not judged either way. **LFE**, a signal check, reads the LFE channel's spectrogram: content an octave above the 120 Hz crossover within 20 dB of the LFE's own bass fails, as a missing low-pass, and content as loud as its bass fails as a full-range channel in the LFE's place, most likely channels in another order. A silent LFE passes, so every LFE is recorded as looked at, and files analysed before have it added from their stored spectrograms, without decoding them again. An ADM master suggests the Atmos profile; a workspace's own profile can ask for a layout, or for Atmos, from the same Layout menu. The QA view shows an ADM master's bed, objects and programme under its embedded metadata, as the prototype does, and the report lists the same.

## 097. The QA list narrows, and a new thread can be filed as it is written

## 098. A recording's channels are heard apart in the browser

The player hears a recording's channels apart (#74), as the prototype's audio layout menu does: a Channels button beside View opens, under the player's controls as the View settings do, a row for each speaker (L, R, C, LFE, Ls, Rs, as engineers name them from the file's layout) with solo and mute, and, for anything wider than stereo whose layout names each channel, "Hear the stereo downmix" (a file that does not say which speaker each channel is gets no downmix, rather than one that guesses). It is done in the browser with Web Audio over the stream that plays, so no new rendition is made and nothing leaves the protected delivery path: the channels are split, each given its level, and either folded to stereo (ITU-R BS.775: the front pair whole, the rest at −3 dB, the LFE left out, scaled so neither side sums above full scale, as ffmpeg's own downmix for the AAC is) or passed through as recorded, a device with fewer outputs folding them down itself. Nothing passes through Web Audio until someone first changes the mix, so ordinary listening is untouched. A stereo file's channels can be heard apart in any rendition; a wider one only in the lossless stream, which carries every channel (the AAC is a stereo downmix, and a Dolby stream is decoded as the browser sees fit), and only up to eight channels, the most a browser plays from one stream. Otherwise the panel says why and what to choose. Each channel's row also shows its level at the playhead, as the prototype's rows do: the RMS the worker measured, read from the stored loudness series, so no audio is analysed in the browser, dimmed for a channel muted or not soloed, and shown only to those with the meters. A pair of channels whose file does not say how they are laid out is left and right, as the loudness meters name it; anything wider is numbered. Binaural listening is decision 103; wider layouts follow separately.

## 099. A recording plays slower or faster, its pitch kept

## 100. The front pair's mid and side are metered as it plays

Beside the phase meter, the loudness panel meters the front pair's mid, (L+R)/2, and side, (L−R)/2, as RMS at the playhead (#34), as the prototype's meters do (M, S and the correlation): a side close to the mid is wide or out of phase, a side far below it narrow. They are measured with the loudness, from the same sums that give the correlation, so no audio is analysed in the browser and nothing more is decoded, and they are stored as two more values a frame in the loudness series, marked by a flag, so a series measured before reads as it did. ## 101. The waveform zooms to the finest peaks kept, not to the sample

A recording's waveform and spectrogram zoom in (#34), a doubling at a time, with the zoom buttons beside the player's controls or `=`, `-` and `0` (back to the whole file), as the document viewer zooms its pages. Zoomed in, the surface scrolls sideways and keeps the playhead in view as it plays or is moved, a page at a time as a DAW does; the moment under the playhead (or the middle, when the playhead is out of view) stays put as the zoom changes. Clicks still seek and drags still loop on it; the scrub bar under it keeps the whole file, with every comment and finding, as the overview. A file zooms until each pixel across the player has a stored peak of its own (256 samples, about 5 ms), and no more than 64 times; a file too short for that offers no zoom. #34 asks for zoom to sample level, but individual samples are the audio itself: drawing them would mean sending the browser something from which the audio can be rebuilt outside the protected delivery path, which the peaks were designed never to be (see `docs/security.md`). So the finest zoom is the finest peaks level, and sample-level zoom waits on a decision about that trade.

## 102. A version's edit decision list is read against the track's takes

A version's edit decision list (#56), given when the version is made or afterwards from its menu (by those who may organise the project), is read on the server as a CMX 3600 list, the form every editor and DAW exports: the title, the frame count mode, each event's reel, tracks, transition and source and record timecodes, and the clip name noted under it. Events of no length (the cut that opens a dissolve) and lines it does not know are passed over. The timecode rate is 29.97 for a drop frame list; otherwise the list does not say, so it is worked out from the frame numbers (a frame 27 means 30) or taken as 25, and whoever reads it can set it. The version's timeline is taken to start on the hour its first edit falls in (01:00:00:00, most often).

Each event's source is matched to one of the track's takes: by its clip name, then its reel, against the take's file name or label (case, spaces, punctuation and extension aside); then by a reel cut short from the file's name (eight characters, in a strict list); then by a take number written as T12, TK12 or Take 12. Black and auxiliary sources are no take. The take's own timecode (Broadcast Wave's time reference) is where its file starts, so the source timecode less that is where in the take the edit begins; a take with no timecode starts at zero, and a place that falls outside the file is left unknown rather than guessed. Where the take has bars, its bars are spread evenly over the part that counts (its in and out points, or the whole file) to say which bars the edit uses, as near as that can say.

The takes view shows it, as the prototype's Edit decisions does: each edit in order, with its place in the version, the take it comes from (or the source the list names, where it is no take of this track), where in the take, and which bars; the takes the version uses are marked "in V3", with their bars under their lane, which answers "which take is used at bar 72" alongside the takes covering it. A bar thread's Other takes marks the take the list uses at that bar the same way ("in V3"), and the takes view can show only the takes the list uses ("In V3"), as the prototype's take manager does. It needs `view_takes`, as the takes do. The list is text about an edit, not media: it is read on the server and nothing new reaches the browser but the matches. Pyramix's and Sequoia's own formats, and a project's upload rule reading the list rather than only asking for one, follow separately.

## 103. A surround recording can be heard binaurally, on headphones

Beside the stereo downmix, the Channels panel offers "Hear it binaurally, on headphones" (#74), one or the other: each speaker of a layout that names its channels is placed around the listener where ITU-R BS.2051 puts it (the front pair at 30°, 5.1's surrounds at 110°, 7.1's sides at 90° and rears at 135°, the height layer 30° up) and rendered through the browser's own head-related transfer function (Web Audio's HRTF panner), with no fall-off for distance. The LFE has no place and goes to both ears at −3 dB, and the whole is scaled by the number of speakers so a wide layout is no louder than stereo. As with the downmix, it is done over the stream that plays, so nothing new is made or sent; solo and mute apply before it, and it is offered only where every channel is an LFE or a speaker with a known place (the wides, surround directs and bottom layer among them), never guessing where one stands. It is a reviewer's monitoring aid, not Dolby's or any renderer's binaural: an ADM master's objects are not rendered (decision 096), only its bed as channels.

## 104. A thread can be about one channel

A comment on a recording of two channels or more can say which channel it is about (#74): the composer offers "Every channel" (the default) or one of the recording's speakers by name (L, R, C, LFE and so on, or Channel 3 where the layout does not name them), and the thread shows it beside its category, as the prototype's thread does. It is stored as the channel's index on the comment (`comments.channel`, null for every channel), checked against the channel count the file was probed with (a mono recording has none to be about), and a reply takes its thread's channel rather than naming its own. A comment begun from a QA finding on one channel is about that channel. Carried to a later version, the thread is about the same speaker there where both versions name their channels, the same place where they have as many, and otherwise every channel, never the wrong one. An export of the comments says it too: a marker's name begins with the channel in brackets ("[L] Mira Solberg: ..."), the spreadsheet gains a last Channel column ("Every channel" where none is named, so existing columns keep their places), and the text sheet shows it beside the time. It says where to listen; it does not mute or solo anything for whoever reads it, which stays the Channels panel's job.

## 105. The stereo field is measured with the other meters and drawn as a goniometer

The QA view's meters at the playhead gain the stereo field of the front pair (#34), as a goniometer draws it: a half disc with mono straight up, the left and right speakers 45° either side and out of phase flat across, filled where the energy is. It is measured once with the phase, mid and side, not live in the browser: for every 100 ms frame the analysis puts each sample of the pair at its angle (mid up, side across, the trace through the middle reading the same both ways) in one of 16 bins of 11.25°, so mono, each speaker and out of phase each have a bin centred on them, and keeps each bin's share of the frame's energy (the loudness series, flag bit 2, in ten-thousandths). That makes it read the same paused or at any point as playing, like the other meters, and costs 32 bytes a frame. The shape is drawn at the square root of each share against the largest, so a quiet direction still shows; under it the reading is put in words ("Centred", "Leans left", and how much lies beyond the speakers where that is 5% or more), which is also what a screen reader hears. Beyond the speakers is not called out of phase: unrelated left and right (a wide room, a reverb, different parts on each side) put some energy there too, a little over two fifths (44%) for wholly unrelated sides of equal level, so the shape turns to the signal colour only where more than half lies there, which only material out of phase does. Files measured before it have no field and show none until they are measured again.

## 106. Marker lists are read in the browser, by their contents

A marker list from another application (#134) is read by pure parsers in `packages/shared`, so the browser can show what it found before anything is sent, and only the markers chosen reach the server, which checks them like any comment. The format is told by the contents, never the file's name: a MIDI file's header; Final Cut Pro's or Premiere Pro's XML by its root; Pro Tools' session text by its markers heading; Reaper's list by its header; DaVinci Resolve's marker EDL by its marker notes (an edit decision list without them is refused as having no markers); Media Composer's tab-separated marker text by its timecodes and colours; a CSV by headings it knows (a time, and a name or comment, in any order, with commas, semicolons or tabs); and otherwise plain text, a line a marker, beginning with a time. These are the formats the comment export writes (decision 052), so every export reads back to where it was; Pyramix, SADiE and Sequoia wait for lists exported from them (#233), and Nuendo's lists are read as the CSV the export writes for it.

Times come back in seconds from the start of the file. Where a list counts in timecode it is read at its own rate if it gives one (drop frame, a Pro Tools session's timecode format, an XML sequence's rate), otherwise at the lowest rate its frame numbers fit; 23.976 and 29.97 count their frames as 24 and 30 do, each a thousandth longer, and a ";" before the frames means drop frame whatever else is said. Its timeline is taken to start on the hour its earliest marker is labelled with (01:00:00:00, most often), counted at the same rate, as for an edit decision list (decision 102). Lists that say where they start use that: Final Cut Pro's `tcStart` (each marker placed through its clip's offset and start), Premiere's frames from the sequence's start, Pro Tools' samples from the session's start, a MIDI file's ticks through its tempo map. A time the list writes in bars and beats cannot be read without the session's tempo and is shown as unreadable rather than guessed. Text is UTF-8, else Windows Latin-1, or UTF-16 where a byte order mark says so. A list brings at most 2,000 markers.

## 107. Importing a marker list is triage's, and each comment says where it came from

The file's menu offers *Import a marker list…* (#134) to those who triage, beside *Export comments…*, on a recording or a video: the import says whose markers they were and which category each of the list's colours becomes, which are triage's choices. The dialog reads the list in the page (decision 106) and shows every marker with its time and what it says, those that cannot come in marked with why (no time it can read, before the start or past the end of the file, saying nothing); a timecode rate worked out from the frames can be changed there. Each comment comes in at its marker's time (a range where the list gives one) or about the whole file, as chosen; its text is the marker's name with its comment under it.

The author is the importer unless they choose another member of the project (the people a comment there could mention), so a producer's markers from their own session can stay theirs. Each comment keeps the list's name and who imported it, and the thread says "from Maple V2 markers.txt", naming the importer on hover (not to guests), so a comment never reads as written by someone who did not write it here. The comments are written together, each checked as its anchor would be on its own (a marker past the end refuses the import, saying which), and the import is one entry in the access log (`comment.import`, with the list's name and how many). Nobody is notified of each comment, as a list can bring hundreds.

## 108. A file's comments print as a sheet the server makes

Beside *Export* in the export dialog, *Printable sheet* (#134) downloads the same threads as a PDF, whatever application is chosen: the scope chosen there (open threads or all, with or without replies), numbered in the order the export writes them, each with where it is (as the comments column writes its anchor, in the video's timecode for a video), the channel it is about, who wrote it, whether it is resolved, its text and its replies. It is stamped as the QA report is (decision 090): the workspace, the project, who asked for it with their part in the project, and when. The server makes it with the same plain PDF writer as the QA report (A4, Helvetica, nothing embedded), so it prints the same everywhere and needs nothing in the browser; it is an export by another name, so it is triage's, and it is in the access log as `comment.export` with the target `sheet`.

## 109. Phase can be read between any two channels

A multichannel recording's phase meter (#74, #34) offers *Phase between*, listing every pair of its channels by their speakers' names ("L–R", "Ls–Rs", "C–LFE"), the front pair first; the reading at the playhead is that pair's correlation. The analysis measures it with the front pair's, from the same decode: for every 100 ms frame, each channel's power and each pair's product, so each pair's correlation costs a multiplication a sample and nothing more is read. It keeps every pair for recordings of up to eight channels (7.1: 28 pairs, 56 bytes a frame, in the loudness series under flag bit 3); a wider layout (7.1.4 and up) keeps the front pair only, as the number of pairs grows with the square of the channels and an immersive bed's height pairs are read in the QA view's channel checks rather than here. The mid and side, and the stereo field, stay the front pair's. Files measured before it show the front pair alone until they are measured again.

## 110. A version's edits lie under its waveform

A recording that is a variation of a version with an edit decision list (#56) shows the list's edits as a lane under its waveform, for those who may see the track's takes: each stretch of the version named by the take it comes from ("T3") and the take's bars, or by the source as the list names it where it is no take of the track. The lane reads as cuts: an edit filling two tracks of the list is one stretch, and where edits overlap, as a dissolve does, each later one starts where the one before ends. The edit playing is lit. A click on the lane goes to the start of the edit it lands on, to hear the cut into it; dragging on it makes no loop, as it stands for edits rather than time. A screen reader hears the edits as a list (take, bars, where in the version) and the lane as the edit playing. The list is the one attached to that version, read and matched to the takes by the same route as the Takes view (`?version=`), so a version without a list shows no lane, and a guest never sees one. The stretches are worked out in the page by a pure function (`editSegments`).

## 111. The upload rule reads the edit decision list it asks for

Where a project asks for an edit decision list with every version (#131), the list a new version brings is read as well (#56), with the same CMX 3600 reader as the Takes view. A list with no edits Hekate can read is refused (`edl_unreadable`), and so is one whose last edit ends more than a second past the end of the version (`edl_too_long`), measured against the longest of its variations: that is most often another version's list, picked up by mistake. Each refusal names the list and, for a long one, where it ends and where the version does; whoever may edit workflows can let it through, as with the other checks, and the access log names the check. A version is judged on its length only once every variation has been probed, as the one still being probed may be the longest. Edits whose sources are no take of the track are not refused: a pick-up recorded apart is a legitimate source, and the Takes view names it. Without the rule, a list attached to a version is not checked. The checks are one pure function in `packages/shared` (`versionRefusals`); the server reads the list from storage through the same helper as the edit decisions route.

## 112. A track or a review can be followed by choice

The page of a track and of a review has a *Follow* button in its header (#110), pressed and reading *Following* while you follow it, as GitHub's Watch and Linear's Subscribe are: following a track tells you when a new version arrives, and following a review when someone decides, gives feedback or opens it as a guest, by the same notifications and preferences as everything else. Making a track or adding its versions already follows it; whoever asked for a review is told anyway, so they have no button there, as following would change nothing for them. The button is for everyone else who wants to keep up, and for stopping. Guests have no button, as they have no inbox. It stays on an archived project's track, as following is the member's own choice rather than a change to the project. On a phone it is the bell alone (named for screen readers), as is *Compare*, so the page's primary action stays in view; while the follows load it holds its place, disabled, so the header does not move. The account's *Following* lists every follow, with *Unfollow*. Following needs only to see the track or review, which the server checks.

## 113. A take is auditioned at the bar against the recording

From a bar thread's *Other takes* (#46), *Audition* brings a take into the recording's comparison (#137) as its second source, heard first: the take is lined up so that the bar sits where the thread was written (the moment a bar comment keeps), the passage is looped for the bar's length, the two are level-matched by their integrated loudness, and 1 and 2 flip between them at the same place, as the prototype shows. Where the bar lies in a take is worked out the way an edit decision list's bars are read (decision 110's `barsUsed`): its bars spread evenly over its in and out points, or the whole file (`barSpan`, in `packages/shared`). A take without bars or a known length cannot be placed, and a bar thread without a moment (one written on the score's own page) has nothing to line it up with, so neither offers *Audition*. The takes shared on a bar thread offer the same *Audition* in their list, which closes to show the comparison (the prototype's attached-takes dialog plays them inside itself; the comparison under the player does the same job without a second player). Every take in the list, and every take shared on a bar thread, also opens in its own player looped on that bar. The take is a source like any other in the comparison: it plays through the protected path, only for those who may hear it.

## 114. Recording sessions, in a project's Production area

A recording session (#21, #45) is a day or a sitting: its name, the day, where it was, and the tracks it recorded, many to many, as decided for #21. A take still belongs to its track; it now also says which session it was recorded in (`takes.session_id`, optional), as the prototype's data does, so a session can list the takes made in it. Giving a take a session of its project links the session to the take's track if it was not already; a session of another project or workspace is refused as not found. Deleting a session leaves its takes with their tracks, no longer naming it.

Sessions are seen and changed with the takes level of a role's access (`view_takes`, `edit_takes`, "Sessions and takes"), and an archived project's are read-only. They live in the project's **Production** area, as in the prototype: a sidebar item shown on music projects to the roles that see takes, which for now opens on the sessions (the prototype's other production sections, from #47, come with their features). The sessions list shows each with its day and place, its takes and how many are starred, its tracks and how long its takes run; a session's page shows when and where, the tracks it recorded and the takes made in it, each with its track, rating, bars and notes. A take's session is chosen where the take is edited. Importing a day's files and proposing the sessions, takes and tracks builds on this (decision 115).

## 115. A day's takes are imported by proposal, read in the browser

*Import takes* on a project's sessions (#45) takes every file of a day's recording, dropped as files or a folder, and proposes how they are organised before anything is uploaded: the browser reads each wave file's header (format, length, bext and iXML, with its track list), a few kilobytes a file however long it runs, by the same bext and iXML readers the media worker uses, now in `packages/shared`. The proposal is a pure function (`proposeTakeImport`):

- Files make a take by their take number (iXML's, or the file name's through a pattern such as `T{take} {mic}`), else by starting within a second of one another, as a recorder writes one file per microphone from the same moment.
- A take is heard by its summed mix: the file named so (mix, sum, LR, stereo) or the one stereo file among mono microphones, or the only file; where none stands out, someone chooses.
- Takes make sessions by the day they were recorded (bext), else the recorder's tape, else their folder; a day an existing session was recorded on adds to it, and files that give no day add to the session of the name they propose, as an earlier import of them made it.
- Takes go to tracks by name: the scene, the description or the folder against the project's track names, with how sure (the same name, one held in the other, or words in common); a project of one track takes them all, less surely. Matching by the audio itself needs the media worker and comes later.

The proposal is corrected in the dialog (a track or the mix per take, a session's name, a track or leaving out for a selection), each correction undone in turn, and what cannot be placed is listed with why. Importing makes the new sessions, uploads each take's mix into its track's folder (resumable, as every upload), and makes the files the tracks' next takes in their sessions, twenty at a time (`POST /api/projects/:id/takes/import`, `edit_takes`, with the upload permission to send the files). Until the takes already in those sessions are known, nothing is proposed. Importing the same files again proposes their takes as *Already imported* where their session already holds a take made from a file of that name, and the server skips a file that is a take already, so an import stopped part way carries on without making anything twice. *Stop* stops it at once: a mix uploaded and not yet made a take stays a file in its track's folder. A take's other microphones are not uploaded yet: a take is its mix until takes hold a file per microphone.

## 116. The workflow engine is a pure state machine in `packages/shared`

The model of decision 040 is defined once, in `packages/shared/src/workflows.ts` (#25): the node types with their outcomes (as the prototype has them), and zod schemas for a definition (nodes, connectors, groups) that the server stores and the builder edits. Two things the prototype writes as text are structured, so the engine can act on them: a connector's **condition** tests the item's kind, a tag it carries, or whether a member or a guest made the decision that led there (each can be turned round); a loop's **until** is a bound, the most times it is taken in a run. Which connectors are loops is read from the graph (a connector back to a node on the way to it), not from where nodes sit on the canvas.

The same functions check and run a workflow, so the builder's simulation is the engine:

- `workflowProblems` applies the rules: errors (nothing starts it, an action with nothing before it, an event that leads nowhere, something after a finish, an outcome a node does not have, a connector to a node that is gone) keep a workflow from running (`startRun` refuses it, naming the first); two connectors may not share an id, as a loop's bound is counted by its connector; warnings (an action that leads nowhere, a loop without a bound) do not.
- `startRun` and `completeNode` move a run on and say what to do: start an action and wait on it (an approval, feedback, a task, the checks, a wait), listen for an event in mid-flow, do something at once and carry on (notify, share, move), set the status, cancel what is under way, finish. The server carries each effect out, as pg-boss jobs, and logs every transition.
- An action that several branches lead to waits for those still under way (every connector an outcome takes is decided before any node it reaches is entered, so a sibling arriving at the same time counts, as does an immediate action whose outcome is still to be followed) (the soloists' feedback beside the conductor's second round, both before the label's approval); a finish ends the run on the first branch to reach it, cancelling the rest; an event is listened for at once. A run with nothing left to wait on and no finish has *stopped*.
- Every loop is bounded at a hundred passes, with or without an until, and one step passes through at most two thousand nodes, so no definition can keep the engine going.

Storing workflows and runs, starting them from real events and carrying out their effects come next, then the builder (#26) on the same model.

## 117. Workflows run for a track, each move logged

A workflow that is switched on runs for a track (#25): its **run** keeps the definition and version it started with (`workflow_runs`), so a later edit to the workflow never changes a run under way, and every move it makes is logged (`workflow_steps`: the node that ended, by which outcome, who ended it if someone did, and what the engine said to do). One run of a workflow goes at a time for a track, held by the database.

- **Starting.** A new version of a track starts each workflow that runs for it (its own, or the project's, as decision 040 has it) from its *A version is uploaded* trigger. A run under way on the track takes the version at an upload it waits for in mid-flow, whatever has since become of its workflow (switched off, changed or removed), as a run keeps its definition; one that waits for none goes on as it was. A workflow switched off starts nothing new. A workflow whose trigger is *Started by hand* is started from the track by those who edit workflows. A workflow that cannot move on never keeps the version back.
- **What a run does.** *Set status* (and the status an action carries) sets the track's workflow status. *Notify* tells the role it names (or everyone in the project), in the app and by mail as each person chooses (a new notification kind, `workflow`). A *task* tells the role it names that the stage is theirs. A *wait* is a job queued for its days; it ends its node only if the run still waits on the step that began it, and an hourly sweep ends any wait whose days have passed, so one whose job was never queued (the queue down, the process stopped) still ends. A *finish* ends the run, with its status.
- **By hand, for now.** Until tasks (#140) are wired to the stages that ask for them (reviews are, by decision 118, and the checks by decision 119), those who edit workflows end a waiting stage by hand, by one of its outcomes, from the run; the log names them, and a connector's condition on who decided sees a member. Share and move are carried out by decision 121.
- **Seeing it.** A track's runs, newest first, with what each waits on, its status and its log, are seen with the workflow level of a role's access.

## 118. A workflow's approval and feedback stages ask for real reviews

When a run reaches an approval or a feedback stage (#25), Hekate asks for the review it stands for, through the same code as a person asking from the project (`requestReview`), so it is checked, audited and announced alike:

- **Of what.** The track's version whose arrival started the run (else its latest), titled by the stage and the track ("Label approval: Maple Leaf Rag").
- **Of whom.** The stage's *who* names roles or groups of the project, by name, several separated by commas; a role brings every member holding it, a group comes as itself. It may name guests too, as decision 121 says. *In turn* asks them in the order they joined the project; otherwise all at once. An approval is approved when everyone approves, or any one where the stage says so. *Due in days* sets its due date.
- **As whom.** The member the run started with (who added the version, or started it by hand), else whoever made the workflow: the review is theirs, as if they had asked, and they hear its decisions. The workflow, made by someone who may edit workflows, is what authorises it; that person need not be allowed to request reviews themselves.
- **Its outcome.** When the review completes, its stage ends by the matching outcome (approved, changes requested, or feedback submitted), and a connector's condition on who decided sees whether the last to decide was a member or a guest. A run that has moved past the stage is left as it is.
- **Moving past it.** A stage the run no longer waits on (a finish reached by another branch) has its open review cancelled, with the reason that the workflow moved on and the time. The review is asked for only while the run, locked as it is inserted, still waits on its stage, so a stage the run has already moved past is never asked for.
- **When it cannot be asked.** Where the stage names no role or group of the project, or nobody is left to ask it as, the stage waits to be ended by hand and the run's starter is told why, in the app.

## 119. A workflow's checks stage ends by the quality reports

A *Run the checks* stage (#25) is ended by Hekate, not by a person: it reads the quality report (decisions on #41, #43, #74 and #144) of every file of the track's version that started the run (else its latest), as the project wants its checks, and ends by the worst of them.

- **Its outcome.** *Failed* when any check fails, or when a recording or video could not be read or measured (its probe found nothing it could read, or its analysis failed); *warnings* when any check warns; *passed* otherwise. A version with nothing to check (a score, a picture, a video without sound) passes.
- **When.** At once where every file has been measured; otherwise when the last one has, as the media worker says so (a `workflow-checks` job). The hourly sweep that ends waits (decision 117) ends these too, should that job have been lost. A run that has moved past the stage is left as it is.
- **By hand.** Those who edit workflows may still end it by hand, by one of its outcomes, as any stage; a file whose measuring never finishes would otherwise hold the run.

## 120. A stage given days until it is due ends overdue when they pass

A feedback or task stage given days until it is due (#25) starts a clock when a run reaches it, as a wait does (decision 117): a job queued for when its days run out, which the hourly sweep stands in for should it be lost.

- **Its outcome.** If the run still waits on the stage when the clock runs out, the stage ends by *overdue*, done by Hekate rather than a person; a stage ended first (feedback submitted, a task done) is left as it is, and so is a stage the run has reached again since, which has a clock of its own.
- **The review.** A feedback stage's review, due at the same moment, stays open: late notes are still welcome, though they no longer move the run.
- **Not approvals.** An approval has no *overdue* outcome; its due date only reminds its reviewers, as any review's does.

## 121. A workflow's share and move stages are carried out

A run's *Share* and *Move to a folder* stages (#25) are done by Hekate at once, and the run carries on from them, as from a notification.

- **Who a stage names.** A stage's *who* (a share's *to*) names, separated by commas, roles and groups of the project by name; guests of the workspace by the name they are known by, followed by "(guest)", as the builder offers them ("Mira Solberg (guest)"); and anyone by email, with their name before it in angle brackets where they are new ("Ines Arlow <ines@example.test>"), who becomes a guest as when a person asks them. Approval and feedback stages read it the same way (decision 118). Someone named twice is asked once.
- **Share.** A share (decision 095) of the track's version that started the run (else its latest), made through the same code as one a person makes, as the run's starter (else whoever made the workflow): titled by the stage and the track, for the people its *to* names, lasting its *expires in* days where it gives some. Nothing waits on a share, so the run is not held by it, and moving on never stops it. When nobody it names can be found, the run's starter is told why.
- **Move.** The track is filed in the folder its *folder* names, by its path from the top of the project ("Masters", or "Masters/Final"), its names matched whatever their case, though a folder written exactly as it is comes first, and folders differing only by case are not guessed between; none is the top of the project. The folder is held while the track moves, so it cannot be deleted under it. When the project has no such folder, the run's starter is told and the run carries on, the track left where it was.

## 122. A workflow is kept and shared as a YAML file

A workflow (#145) can be written out as a file and read back in, so it can be kept in a repository, shared between projects or moved to another instance, as a dashboard is exported from a monitoring tool. The format is documented for people at *Use, Workflow files*.

- **YAML, read by Hekate itself.** The file is YAML, which people can read and edit by hand. `packages/shared` may depend on nothing but zod, and the server and the builder must read a file the same way, so Hekate reads the part of YAML the format needs (mappings and lists by indentation, plain and quoted values, lists in brackets, comments) in `workflow-files.ts`; anything else is refused with its line rather than guessed at.
- **Versioned.** A file starts with `hekate: workflow/1`. A later format gets a new number, and this one stays readable.
- **The workflow, not its place.** A file holds the steps, connectors, conditions, loops' bounds, groups and positions, but neither the project nor whether the workflow is active: it is switched on in the builder, once its problems are fixed.
- **Refused or listed.** What cannot be drawn (an unknown key, step type or outcome, a connector to a step that is not there, a value outside the model's limits) refuses the file, each mistake with its line, before anything is saved. The builder's rules (decision 040) are listed against their lines as problems, as on the canvas: a draft may have them, a running workflow may not.
- **Templates are files.** The workflows Hekate offers to start from (Simple approval, Conductor first, Parallel stakeholders) ship as files in `packages/shared/src/workflow-templates`, and each must read without a problem and write back as the same text.

## 123. A workflow on the canvas stays legible, and Tidy up lays it out

The builder's canvas (#26) draws whatever positions a workflow's steps have, often placed by hand. It keeps them legible as drawn, and offers to lay them out again, as n8n's Tidy up does.

- **Chips, not labels at ports.** What a connector is (the outcome it leaves by, where its step has several, and its own condition or loop bound) is a chip at its start, beside its port. Ports sit further apart than a chip is tall, so chips beside one step never meet; each connector runs straight past the widest of its step's chips before it turns, so no line crosses another's chip. Where steps sit too close for a chip, it is cut short, its full words shown on hover, and where it would say nothing, its port names the outcome instead.
- **Loops beneath, in lanes.** Loops, and connectors whose target is too far back to curve to, run beneath the workflow, each in a lane of its own: the shortest nearest, so a loop inside another never crosses it, and loops leaving or entering one step side by side.
- **Tidy up, by dagre.** Tidy up (on the canvas's controls, a workflow's menu, or Shift T) lays each workflow out in columns by the order a run reaches its steps, with dagre, an MIT-licensed layered-layout library, which n8n's Tidy up also uses. Hekate's code is its own: n8n's source is published under its Sustainable Use Licence, which cannot be combined with AGPL-3.0, so it was read for the idea, not copied. Loops are left out of the layering so they run beneath; each column is as wide as its own chips need; a stage's steps are kept together; the way most items go (each step's first outcome) stays on one row, side branches hang below it, and no step sits in the row between two steps joined by a straight line. The workflow keeps its place on the canvas; only positions change, saved as any move is, and Undo puts them back.

## 124. Tasks are a project's own, and a thread's to-do is one of them

Tasks (#140) are rows of their own (`tasks`, with `task_events` for their activity), not a flag on a comment: they may be made by hand, about a track or a file, or by a workflow's task stage, and have an owner, a priority, a date and four statuses (to do, in progress, needs approval, done).

- **A thread's to-do is a task.** Making a thread a task (decision 067) makes one of its project's tasks, titled by the thread's first line and linked to it; one thread has at most one, and deleting the thread deletes it. The comment's to-do columns are gone: migration 0083 turned every thread already made a task into one, numbered in the order the threads were written, done where they were done. The comment API still says `todo`, `todoDoneAt` and `todoDoneByName`, now read from the task, and gives its `taskId`.
- **One owner for both.** A thread's task is for whoever the thread is for: assigning either assigns the other, and its activity says so.
- **Keys are never reused.** Tasks are numbered per project from a count kept on the project, raised as each is made, so two made at once never share a number and a deleted task's number is not given to the next. Its key is the project's initials and its number (`taskKey`).
- **Rights are a pure function.** `taskRights` in `packages/shared` decides who may do what, from the viewer's role and their part in the task: writing in the project is the floor (so nothing changes in an archived one); its creator and those who triage edit, move and delete it; whoever it is for moves it along but neither edits it nor approves their own (a task needing approval is closed by its creator or triage); anyone who writes may add a note. The server checks it again on the row as it locks it.
- **Visibility follows the project** (decision 024): whoever sees the project sees its tasks and may export them as a spreadsheet, with any cell that could read as a formula quoted. The comment a task came from is shown in it only to those who may read comments. Guests see no tasks.
- **A workflow's task stage makes a task** (#25): titled by the stage, about the track, for whoever the stage names where it names one person (else nobody, and those it names are told as before), due when the stage's due days run out. It has no creator, so those who triage run it. Marking it done ends the stage done, if the run still waits on it and it is the task the stage made last (a loop back makes a new one); ending the stage done by hand marks its open task done too. A stage that ends overdue, or that the run moves past, leaves its task open, late where it is.
- **Notifications** (#110): someone given a task is told, as is a task's creator when it waits for their approval, under the new *task* kind. Whoever a task is for is reminded of its date on the day it is due and once it is late, each once and from eight in the morning in their own time zone (`taskReminder`), by the hourly reminder job; a new date starts afresh, and a done task is never reminded of.

## 125. The board groups tracks by what their workflow says, and is arranged by each person

A project's board (#141) shows every track as a card in a column, as Linear's board shows issues.

- **Columns come from the workflows.** Grouped by status, the columns are the statuses the project's switched-on workflows set, in the order a run reaches them; a finish's status reads as done. Grouped by stage, they are the steps a track can wait at (approvals, feedback, tasks, checks, waits, shares). Tracks with no version come first, then (only while there are any) versioned tracks the workflow has not yet given a status or a step. A status a track still holds that no workflow sets any more gets a column of its own, so no track is ever missing. The rules are pure, in `packages/shared` (`boardColumns`, `boardColumnOf`).
- **Cards say where it stands.** Its latest version, the step its running workflow waits at, whom an open review of it waits on and by when, what its latest review's reviewers said, its open tasks and, for those who may read comments, how many threads on its latest version are open. Whoever sees the project sees its board.
- **Arranged by each person.** The grouping, what cards carry, which fields and which columns are put away are the viewer's own, kept with their account (`board` in their preferences), as the prototype's Customise menu has them.
- **Fresh within seconds.** The board asks again every fifteen seconds, so a transition made elsewhere shows without reloading.
- **Not yet.** Moving a card by dragging it is left out: the prototype has none, and a track's status is the workflow's to set. The calendar, its subscription and the timeline follow in parts of their own.


## 126. A project's calendar, and a feed of it that only its owner's access opens

The board's Calendar view (#141) shows a month of the project: reviews due (not cancelled), tasks due, and, for those who may see takes, the days sessions were recorded. Each opens where it is; one past its date and not finished is marked late. At phone width the days carry dots and the month's events are listed under the grid, as Apple Calendar does.

- **A feed for any calendar.** *Add to your calendar* makes a link to an iCalendar feed of the project (`/api/calendar/<token>.ics`) that Apple Calendar, Google Calendar and Outlook subscribe to. Its events are all-day, with the date, the title and a link back; nothing else of the project is in it.
- **The link is the credential, so it is treated as one.** It is 32 random bytes, shown once as it is made; only its SHA-256 is kept (`calendar_feeds`), so the database alone opens no feed. Each person has at most one per project: making a new one stops the old, and *Stop the feed* removes it.
- **Access is checked on every read.** The feed shows only what its owner may see at that moment: someone no longer a member, a project they can no longer see, or a suspended or closing workspace reads as not found, as does an unknown link. Each read is noted (`readAt`, shown in the dialog), the response is never cached, and the path is rate limited.

## 127. The board's timeline runs each track from its latest version to its review's due date

The board's Timeline view (#141) approximates a Gantt chart, as the prototype does, from what the board already knows rather than from a schedule of its own: each track runs from the day its latest version arrived to the day an open review of it is due, or a week on where none is, labelled with the step it waits at (else its status, else its version). Finished tracks are solid, late ones marked. It shows six weeks from the Monday two weeks before today, moved three weeks at a time; the names stay pinned while the weeks scroll beneath them, and a phone opens it scrolled to today. The rules are pure, in `packages/shared` (`timelineWeeks`, `timelineBar`).

## 128. A project keeps a status set, which the board and the steps follow

Each project has a status set (#26), as the prototype's Statuses panel on the workflow canvas has it: names in an order, each read as to do, in progress or done. It is kept on the project (`workflow_statuses`), changed whole by those who edit workflows, and seen by those who see them.

- **The board follows it.** Grouped by status, the board's columns are the set in its order and with its categories, then any status a step sets that the set lacks, as before (a finish's reading as done). With no set, nothing changes from decision 125. The rule is pure, in `packages/shared` (`projectStatuses`).
- **Steps choose from it.** Once a project has any statuses, a step's status is chosen from them rather than written, so the same status is never spelt two ways; a project with none yet still writes one.
- **The panel lists what is really there.** It shows the set and the statuses only a step sets so far, kept in the set with the first change. A status a step sets cannot be removed until no step does; each name is kept once, whatever its case.

## 129. A workflow is copied from another project by reading it there and making it here

Copying a workflow from another project of the workspace (#26) needs nothing new on the server: the builder reads the other project's workflows as any member does (so only where their role there shows workflows) and makes the chosen one here through the same validated create as a template, switched off and as this project's own, a track's own becoming the project's. Who its steps name (roles, groups) is kept as named; a name this project lacks shows as such in the step, to choose again. It is offered beside the templates in the basic view.

## 130. A track's page says where its workflow has it

A track's versions page carries the prototype's line (#26): the status its workflow gave it, read by the project's status set (decision 128), the step its run waits at, and *Next:* the step it usually reaches after, by the waiting step's first outcome and past anything done at once (`nextStep` in `packages/shared`). It is read from `/api/tracks/:id/workflow-standing` by whoever sees the track, as the board's cards are; the run's log and ending a step by hand stay with those who edit workflows.

## 131. A track's followers hear when its workflow gives it a new status

When a workflow sets a track's status (a step's status, or a finish's) to one it did not already hold, everyone who follows the track is told under the *workflow* kind (#110): "Maple Leaf Rag is now With the label", linking to the track. Whoever moved it is not told of their own move, and a status set again unchanged (in whatever case, decision 128) tells nobody. The track is locked as its run moves it, so two runs moving it at once take turns and its followers hear of one change once. The mail says why it came: the workflow names them or their role, or they follow the track it moved. Stage changes are told as before: those a stage asks are asked, and a notify step tells whom it names.

## 132. Files recorded together make one take though they start or stop apart

Decision 115 grouped files without take numbers by starting within a second of one another. A recorder's microphones do not always: one is armed a few seconds late, another stopped early. Such files now also make one take where both lengths are known and they record together for at least half of the shorter one (`sameSpan` in `packages/shared`). Takes recorded one after another share at most a moment, so stay apart, as does a file with no length that starts more than a second away.

## 133. A new version may start its track's workflow again from a stage

A new version carries its track's workflows on as before (decision 117): a run waiting for an upload takes it, and a workflow with no run under way starts from its upload trigger. Those who edit workflows may instead choose, on the new version, a stage to start one of the track's workflows again from (#25), as the prototype's *Restart the workflow from* has it; *Keep the current stage* is the default.

- **The stages offered** are those a run waits at (an approval, feedback, a task, the checks, a wait), in the order a run reaches them (`restartPoints` in `packages/shared`), of the workflows that run for the track: its own where it has any, else the project's.
- **The run under way stops** (`stopRun`): the reviews it waited on are cancelled, as when a run moves past a stage, and its log ends there. A task it made stays open, as a stage that ends overdue leaves its task (decision 124).
- **A new run starts at the stage** (`startRunAt`) on the workflow as it now stands, as though the workflow had just reached it: its status is set, its review asked for or its task made, and it goes on from there.
- **All or nothing.** The restart is made in the version's own transaction (`restartAt`): the workflow is locked and checked again (switched on, the track's, the stage one of its own), its run under way stopped and the new one started on the definition as locked. Someone who may not edit workflows is refused, and so is a stage the track's workflows do not have; refused, the version is not made either. Starting a workflow afresh takes the same lock, so two versions arriving at once never start it twice.

## 134. A video's own timecode, mattes and safe areas

A video is reviewed on its own clock (#146). The probe reads the timecode its first frame carries (its own stream's, a QuickTime timecode track's, or the container's) and the player counts from it, at the standard rate nearest the file's, dropping frames where the timecode says so with a semicolon at 29.97 or 59.94. A file with no timecode counts from 00:00:00:00, as do files probed before this.

- **Shown**: the timecode and the frame number, counted from the file's first frame, with the file's length beside it as a timecode from zero. Frame stepping lands on each frame's own time, so it never skips or repeats one.
- **Go to** takes a timecode as editors type it: four fields (or eight digits) are a timecode on the file's clock; fewer count from the start, right-aligned, so "12:00" is twelve seconds in. Timecode wraps at midnight, so a label earlier than the file's first is the next day's. A label drop frame skips, or one outside the file, is refused in the field.
- **Mattes** (2.39:1, 1.85:1, 4:3) and **safe areas** are guides over the picture, fitted to the picture rather than the player, so a vertical cut is guided too. Safe areas follow SMPTE ST 2046-1 (action within 93% of the frame, titles within 90%) rather than the older 90% and 80% of standard definition. They take no click and are each viewer's own, for the file in front of them.
- The pure functions (`videoClock`, `parseTimecode`, `matteBars`) are in `packages/shared`, beside the drop-frame timecode the comment export already writes, so a comment's anchor can be shown on the same clock when drawings land.

## 135. Moving a project to another workspace

A project can move between workspaces (#240). This decision covers the move itself (`moveProject` in `apps/server/src/project-transfer.ts`). Who may ask for a move, the second member's approval, the gaining workspace's acceptance, the fresh sign-in and the operator's move are built on top of it.

- **All or nothing.** The project's stored objects are copied under the gaining workspace's prefix first, outside the transaction. Then, in one transaction, the project is locked and every key is rewrapped with the gaining workspace's key. Every row of the project moves, and whatever cannot follow it is mapped or left behind. The old objects are deleted only once the transaction commits. If it fails, the copies are deleted and nothing has moved.
- **Review decisions move as recorded.** They stay append-only, with one narrow exception (migration 0087), chosen by the owner over recreating the reviews or leaving the sign-offs behind. Inside a transaction that sets `hekate.project_transfer`, a decision may change its workspace and nothing else. The trigger checks that every other column is unchanged, so ids, decisions, who made them and when stay exactly as they were. Every other update is still refused, flag or not.
- **What cannot follow.** People who are not members of the gaining workspace lose their place in the project, and tasks and threads assigned to them become unassigned. What they wrote and decided stays theirs. Guests are matched in the gaining workspace by address, or added to it. Tags and custom delivery profiles are matched by name, or copied.
- **What is dropped.** Unfinished uploads, live download tickets and calendar feed links are dropped, because each was given out under the losing workspace. The access log stays where it was written: the project's history before the move remains in the losing workspace's log.
- **Every table is placed.** A test checks that every tenant table is listed once, as moved, dropped or the workspace's own. A table added later must be placed before it ships.
- **Refused** while any of the project's files are still being prepared, while the project is being deleted, or when the gaining workspace is suspended or being deleted. These are checked again inside the transaction, with the project locked for update and the gaining workspace locked for share. A deletion or suspension confirmed while the objects were copying is therefore seen, and one confirmed during the move waits for it.
- **Every query names the losing workspace.** Each read, update and delete of the project's rows carries its `organisation_id`, as every tenant query must. The rows move children first, so each one is still found through parents that haven't moved yet.
- **A checksum still to compute** (a file uploaded in parts whose `blob-checksum` job names the losing workspace) is asked for again under the gaining workspace once the move commits. The old job can then only fail, harmlessly, and no file is left without a checksum.

## 136. Asking for, signing off and making a project's move

Who may move a project between workspaces, and how it is confirmed (#240), on top of the move itself (decision 135). This follows the owner's spec on the issue.

- **Asking.** Someone whose role in the project may delete it (`delete_project`) asks, from the project. They choose one of their own other workspaces, or type another workspace's address. A project whose deletion is asked for cannot be asked to move.
- **At once, or with two sign-offs.** Where the person asking is an owner or admin of the gaining workspace, the project moves as soon as they confirm. Otherwise the transfer waits for two things before anything moves:
  - **approval** by a second member of the losing workspace whose role may delete the project, never the person who asked;
  - **acceptance** by an owner or admin of the gaining workspace.

  Either may come first. A transfer can be refused by either side, withdrawn by whoever asked, and lapses after a week if no one acts on it.
- **Confirmed every time.** Asking, approving and accepting each need the project's name typed in (ignoring letter case and surrounding spaces), and the person themself at the keyboard. That means their password, or their directory password, or, for an account with neither (single sign-on or passkey only), a sign-in in the last ten minutes. This is the same check as deleting an account, now shared as `confirmIdentity`.
- **Moved once.** Each sign-off is claimed in the same update that records it, so of two people signing at the same moment, one does. When the last sign-off lands, the transfer is claimed (`pending` to `moving`) before the move, so it moves once. If the move fails (a file still being prepared, a storage error), nothing moves:
  - a sign-off is taken back, to be given again once the problem is put right, and is written to the logs only once its move has happened;
  - a request that would have moved at once ends, and can be asked again.
- **Not with a deletion.** A project whose deletion is asked for cannot move, checked again under the move's lock. Its deletion cannot be asked for while a move waits, so a deletion asked for under one workspace's roles never travels to another.
- **Lapsed means lapsed.** A transfer past its week is treated as lapsed as soon as anyone reads it or asks again, so it never blocks a new request.
- **Heard and written down.** Every step is written to both workspaces' audit logs. The gaining workspace's entries name the project only by name until it arrives. The people who can act on the next step hear of it in their own workspace (a new `transfer` notification kind), the person who asked hears of approvals and refusals, and both workspaces' owners and admins hear of the move.
- **Operators.** An operator can move a project from the instance side without approval or acceptance, confirmed by typing its name and their password. A transfer waiting on the project is withdrawn, but only once the operator's move has succeeded; a move refused leaves it as it was. The move is kept as a transfer already done, written to both workspaces' logs and the instance's events, and both workspaces' owners and admins are told.
- **Who sees them.** A workspace's owners and admins see every transfer naming it. Other members see only those moving out a project they can see, so no project's name reaches someone who cannot see the project.
- **Stored across two workspaces.** `project_transfers` belongs to both workspaces, so it has no single `organisation_id`. Instead it has `from_organisation_id` and `to_organisation_id`, and every query names the asking workspace as one of them, so each side sees only the transfers that name it. One transfer waits on a project at a time (a unique partial index).

## 137. Drawings on a video's frame, and timecode on its comments

Drawing on the picture (#146), on top of the video's own timecode (decision 134).

- **A drawing is a region anchor.** It is not a new kind of anchor. A region on a video carries the time it was drawn at (`at`), optionally an end (`end`) for a drawing meant to stay over a range, and the `drawing` itself: one tool (box, circle, line, arrow, freehand or text), one of four colours, and its points in the picture's normalised coordinates. The region's rectangle is the drawing's bounds, and the schema refuses one that is not, so anything that reads regions (the comment sheet, exports) keeps working without knowing about drawings and can never point somewhere else.
- **Colours are named, not chosen freely.** Orange (the signal colour), white, blue and green, each a token in `tokens.css`. A drawing never stores a hex value, so it follows the theme and stays legible over any picture.
- **Shown at its frame.** A drawing shows while the playhead is on its frame, or anywhere in its range, and the one being written shows over the others, which fade. While a video with drawings plays, the player follows each frame it presents (`requestVideoFrameCallback`), since the media element's own time updates come too seldom to land on a single frame. Drawings take no clicks, so the picture still plays and pauses beneath them; a drawing's comment label takes you back to its frame.
- **Drawing pauses.** Choosing Draw pauses playback and lays the tools over the foot of the picture. A drag draws a box, circle, line or arrow from corner to corner, or a freehand stroke along its path; a click places text. The drawing joins the comment being written as its anchor; a new drawing replaces it, Undo brings back the one before, and it can be discarded before it is posted.
- **Checked like any time.** A drawing past the end of the video, or ending before it starts, is refused. A new version's alignment moves a drawing's time and end as it moves any other time.
- **Timecode on a video's comments.** A comment on a video is labelled in the video's own timecode, frames and all, where one on audio keeps minutes and seconds.

## 138. Deliverables are tracks in video words

A video project's deliverables, cuts and renditions (#16) are its tracks, versions and variations, not tables of their own. The owner chose this over separate tables on the issue. Decision 015 is reworded to match.

- **One structure.** Workflows, reviews of an item, the board, the timeline, followers, carry-over, tasks and the access log already work for tracks, so they work for deliverables on the day they ship. Separate tables would have doubled each of those paths and their tests, and every later feature would have had to remember both.
- **Video words.** A video project says deliverable, cut and rendition wherever a music project says track, version and variation, and names a cut "Cut 3" where a version is "V3". The words come from one shared function (`itemWords`), so a screen cannot mix them. Takes and scores, which are music's, do not appear on a deliverable.
- **What a rendition is.** Its shape (16:9, 9:16, 2.39:1) and codec are read from the file, never typed, so they cannot disagree with it. Whether it is subtitled or clean, and graded or ungraded, is said by those who organise the project, and stays unsaid (null) until someone says it. A rendition never claims what no one checked.
- **Stored.** Two nullable columns on `variations`, `subtitled` and `graded`. A variation in a music project simply leaves them empty.
- **Changed.** A variation's name and treatment change through one route (`PATCH /api/variations/:id`), for those whose role may organise the project. A treatment is refused outside a video project, so a music variation never claims one.
- **Everywhere.** The file browser shows a video project's deliverables among its folders, as it shows a music project's tracks, and every screen that names tracks (the board, timeline, overview, reviews, comparison, carried-thread history and delivery overrides) uses the project's words. A review carries its project's profile, so a guest's page reads the same as a member's.
- **The shape is the picture's.** It comes from the frame's width and height. An anamorphic file whose pixels are not square would read narrower than it plays; reading the sample aspect ratio can follow when such files turn up.

## 139. A layout wider than eight channels plays in parts

A browser plays at most eight channels from one stream, so a 7.1.4 or wider recording (#74) is carried in two or more lossless streams that play together. The owner chose this over stereo pairs or a downmix only. Decision 098's "up to eight channels" no longer holds.

- **Parts of eight, in the file's own order.** The first part, `flac`, carries channels 1 to 8 (the 7.1 bed of a 7.1.4 mix). The next, `flac-2`, carries channels 9 to 16 (the heights), and so on. ffmpeg picks each part's channels out by index, so a layout ffmpeg cannot name is carried whole as well. Each part is an ordinary rendition with its own content key, and its segments fall at the same times as the first part's.
- **Not an alternative.** A following part is left out of the master playlist, so no player (Safari's own included) can choose it in place of the first. The web player loads it from its own playlist when the lossless stream is heard. A second part costs one more key request, well inside the 30 a minute.
- **One recording in the browser.** Each part plays on a hidden element of its own, following the main player's play, pause, seeks, speed and volume. It is put back on time whenever it drifts by more than 20 ms. All the parts feed the same Web Audio graph, where each channel is the recording's own, whichever stream carries it. Solo, mute, the BS.775 downmix and binaural listening therefore work on every channel. Played as recorded on a device with fewer outputs, a wide layout is folded down to stereo in the graph, as the browser would fold one stream, rather than dropping the channels it has no room for.
- **Where only one element plays.** A comparison source, and Safari's own HLS on iOS (which chooses among the master's renditions itself), play no parts. For a wide layout they play the AAC, a stereo fold of every channel, rather than the first part's eight channels alone; the player names it.
- **Not sample-locked.** The parts stay within a frame or two of each other, which is enough for review listening. Measurements (levels, phase, loudness) come from the server's own decode of the whole file, not from the browser, so they are exact.
- **Earlier files.** A file prepared before this change has one stream of eight; the player says its channels cannot be heard apart rather than playing a partial layout.


## 140. An ADM master's objects are heard through the EBU ADM Renderer

An ADM master (BS.2076, as Atmos and other object-based mixes are delivered) holds a bed of channels and objects whose place moves with the music. Until now only the bed was heard (#74). The owner chose the EBU ADM Renderer (`ear`, BSD-3-Clause, the reference renderer of ITU-R BS.2127) over writing one.

- **Python in the media worker, by exception.** Hekate is TypeScript end to end; the renderer is Python with NumPy and SciPy, and nothing comparable exists for Node. It runs as a separate process, as ffmpeg does, given the decrypted master in the job's private workspace and writing its render there; it opens no network connection and reads nothing else. It is the only Python in Hekate.
- **Pinned, built apart, scanned.** `tools/ear` lists the renderer and every package it needs, each pinned by hash; the dependencies install from wheels only. An `ear` stage of the image installs them with pip into `/opt/ear`; the runtime gets Debian's `python3` of the same version and that directory, never pip or a build tool. ear is published as source only, and is built with a current setuptools that stays in the build stage. ear reads its data files with `pkg_resources`, which setuptools no longer ships (the last releases that did have a known vulnerability), so a four-line stand-in over the standard library's `importlib.resources` serves that one call instead. Trivy scans the packages with the rest of the image; Dependabot moves the pins. CI installs the same pins to run the renderer's tests. `ADM_RENDERER_PATH` names the directory; without it, only the bed is heard, as before.
- **Onto the layout nearest the bed.** The master is rendered onto the BS.2051 system matching its bed: 2.0, 5.1, 5.1.2, 5.1.4, 7.1 or 7.1.4. Any other bed, or objects with no bed, are rendered onto 7.1.4, which holds every bed this side of 9.1.6. ffmpeg then puts the render's channels in its own order for that layout, so the render plays, folds down and is heard apart like any recording of that layout (decision 139 carries a 7.1.4 render in two parts).
- **What the streams carry.** The render replaces the master as the source of its streams, and the file records the layout rendered (`metadata.adm.rendered`); the player hears that layout and names it ("7.1.4 render"). Measurements, the waveform, peaks and the quality checks still come from the master itself. Downloads are the master, untouched.
- **A render that fails** is logged and the streams are made from the master's bed as before, so a file the renderer cannot read still plays. A retry records again what its streams carry.
- **Objects told by their pack.** Reading the master's `chna` chunk, an object is now known by its pack's type (`AP_0003…`), not its track format's, which names the sample format; earlier, every channel of an ADM master was counted in its bed.

## 141. Reviewer permissions per person in a project, and the default roles' tools per workspace

The rest of #55: what the prototype's People page and workspace Defaults show.

- **Per person in a project.** A project's People page sets, for one member or guest, what they may do in every review of the project that asks them: comments they see, commenting, deciding, inviting, tools, download, earlier versions and a play limit. It holds no dates and no items, which belong to one review. It is kept as a change over the workspace's defaults (only what departs from them), so a later change to a default still reaches them. Only those who manage reviewers set it; each change is in the access log; it moves with the project to another workspace, matched to the gaining workspace's guests, and goes with a member who does not.
- **Order.** The more particular wins: the workspace's defaults, then what a request sets for everyone (a workflow stage may), then the person's People page grant, then the request's own override for them. A reviewer added to an open review later gets the review's grant with their People page grant on top. A member's grant still cannot reach past their project role (decision 030).
- **Tool access per workspace.** Workspace settings, Defaults, chooses the player tools each of the five default roles starts with in a new project. Projects made from a template keep the template's roles; existing projects keep their own.

## 142. Video in AV1 beside H.264, and the ladder is the instance's

#148. H.264 plays everywhere a licence for it was paid, and nowhere else: open-source browser builds, some Linux desktops and the browser the visual suite runs do not decode it.

- **A royalty-free encoding at every rung.** Each rung of the ladder is encoded twice: H.264 with AAC, as before, and AV1 (SVT-AV1, a fast preset) with Opus. An instance may choose VP9 instead (quicker to encode, larger) or neither (`VIDEO_ROYALTY_FREE`). Both are packaged, encrypted and delivered like every rendition (decision 022); the playlist names each by its codecs and level, so a browser takes only what it plays. The encode costs about twice what H.264 alone did.
- **One family per viewer.** A player picks one encoding before the stream starts and drops the other's renditions, so the picture never changes codec mid-stream. It takes AV1 where H.264 cannot be played, or where the browser says it decodes AV1 smoothly and power-efficiently; otherwise H.264, which every device decodes in hardware. The browser is asked at the video's own frame rate, as a decoder smooth at 30 frames a second may not be at 60. Choosing a rendition by hand offers the chosen family's rungs, named "720p · AV1". Downloads still make their proxy from the H.264 encoding, which is quicker to decode.
- **The ladder is the instance's.** `VIDEO_LADDER` lists the rungs as height and bitrate, highest first (1080p at 6 Mbit/s, 720p at 3, 480p at 1.2 by default). A video gets the highest rungs at or below its own height, up to `VIDEO_RUNGS` (two). The AV1 or VP9 rung gets two thirds of the H.264 rate. A video rendition advertises its measured peak (RFC 8216's peak segment bit rate) wherever a busy scene took it over its planned rate, so a player never picks a picture its connection cannot keep up with.
- **A GPU where there is one.** `VIDEO_HARDWARE` names a VAAPI render node (Intel or AMD); H.264 is then encoded on it. A rendition the GPU cannot encode (no device, a busy one, a picture it refuses) is encoded again in software, and the worker logs why. AV1 stays in software: few GPUs encode it.


## 143. Cuts compared in the player, their comments and findings on the comparison page

## 144. Captions come from sidecar files, read once into cues

## 146. A video's picture is measured once, beside its sound

#42. A video's picture is checked by the media worker, as a recording's samples are (decision 013): measured once, in the same analysis job, and read into findings that do not depend on the project.

- **One decode.** ffmpeg reads every frame once: field order on the picture as it was made, then the bounds of everything that is not black over the whole video, then black, freezes and levels on a copy no wider than 640 pixels. Its per-frame measurements stream to the worker line by line and are never kept. A silent video is analysed for its picture alone, and a checks stage now waits for it; one probed before this has its picture measured at the next start, as do videos with sound.
- **Black and frozen.** A second or more of black is a note at either end, where films start and finish, and worth a look inside; a picture black throughout fails, however short. Two seconds or more of a picture that does not move is worth a look, unless it is black (already said) or covers nine tenths of the video, which is a still image (a song set to its cover) rather than a fault.
- **Missing frames.** Where the frame rate is known, a gap between frames of one and a half frames or more says how many are missing there. A variable frame rate (a screen recording, a phone) holds a frame as long as it likes, so where more than one frame in twenty is timed off the rate's grid the check says so as a note and counts nothing.
- **Interlacing.** ffmpeg's detector counts frames that look interlaced. A picture truly interlaced keeps one field order throughout, while a progressive one it misreads splits between the two, so only a field order four times as common as the other counts: across four fifths of the frames it is a note ("Interlaced, top field first"), across a tenth or more it is worth a look, as a picture interlaced in places is usually an edit's mistake. Whether interlacing is acceptable is the delivery profile's to say.
- **Broadcast-safe levels.** EBU R103 allows luma from −1% to 103%. Values inside that are moved into the nominal range before ffmpeg counts the pixels outside 16 to 235 (scaled to the bit depth), so the undershoot compression leaves at every black edge is not counted; more than 1% of a frame outside, for a fifth of a second or more, is worth a look. Full-range and RGB pictures, with no headroom to be outside of, are not judged; a picture is full range where its stream says so, else where its pixel format does (`yuvj`). Chroma and RGB gamut are left to the delivery checks.
- **Letterboxing.** Bars the picture never reaches into, over the whole video, more than 1% of the frame on both sides, are a note naming the picture's own shape ("Letterboxed: the picture is 1920×804 inside 1920×1080 (2.39:1)").
- **Flashing.** A first look for screen-wide flashing, not a certified test: the mean luma of each frame is taken as screen luminance on ITU-R BT.1702's 200 cd/m² display, a change of 20 cd/m² or more with its darker side under 160 is a transition, and more than six transitions in a second (Ofcom's three flashes) is worth a look. Flashing in part of the picture, and red flashes, need a dedicated analyser such as Harding.
- **In the product.** The checks sit under Video in a project's QA rules, always on, their severity the project's to change. Their problems are marked along the video's timeline, under its filmstrip, and listed in the QA view and report, whose format line now leads with the picture.

## 147. A video's format and timecode are checked against its delivery

#42. A delivery profile can say what it asks of a video's picture, beside what it asks of the sound, and the picture's timecode is checked for breaks.

- **What a profile asks.** A codec (ProRes, DNxHD or DNxHR, H.264, HEVC, MPEG-2, JPEG 2000, AV1), a size, a frame rate, a scan (progressive or interlaced), colour primaries (Rec. 709 or Rec. 2020) and a range (limited or full); each may be left as any, and a profile that leaves them all asks nothing of a picture. Broadcast (EBU R128) asks for 1920 × 1080 at 25 fps, Rec. 709, limited range; Streaming for a progressive, limited-range picture; the audio-only profiles ask nothing. A workspace's own profile chooses them in its editor, stored with its other numbers, so nothing needed a migration.
- **Picture format.** A delivery check, read against the stored probe whenever it is shown, like the audio's format check: one finding, a pass saying what the picture is ("ProRes HQ, 1920 × 1080, 25 fps, progressive, Rec. 709, limited range"), or a failure naming each difference. A size asked for asks for square pixels too. Frame rates agree within five thousandths of a frame a second, so 23.976 is 24000/1001 while 23.976 and 24, 29.97 and 30, and 59.94 and 60 stay apart. What the file does not say (an older file's probe kept no scan, range or primaries) is not held against it. Aspect follows from the size; audio layout is the layout check's (decision 096).
- **Timecode.** Measured once, in the picture checks' decode: `showinfo` logs each frame's carried timecode (an MPEG-2 group's, or an SMPTE 12-1 timecode from H.264 or HEVC picture timing), and each should be the first plus the frames since, through midnight and dropped frames. One that is not is a break, failed at the frame where it happens ("Timecode jumps from 10:00:01:24 to 11:00:00:00"). ffmpeg's MPEG-2 decoder gives a group's timecode to the frame before it, so a group's timecode a frame early is taken as on time. The file's own records are compared too: start timecodes that differ between the picture, a timecode track and the container, a carried timecode that starts elsewhere than the file says, and drop-frame timecode at a rate that drops none are each worth a look. A file with no timecode is a note; one with only a written start passes, as its count runs on with the picture.
- **Measured again.** Videos whose findings have no timecode check are analysed again at the next start, adding only the checks they lack.

## 149. The take log writes ordinary takes, numbered as the session says

#51, first part. The take log does not keep a list of its own: each take it logs is a row in `takes`, of its track and in its session, so the take manager, coverage and import (#21, #45) see it at once.

- **Lifecycle.** A take is idle, armed, recording, recorded or aborted. It may go from idle or armed to recording, from recording to recorded or aborted, back from armed to idle, and an aborted take may be counted after all; a recorded take stays recorded, never rolled again or aborted after the event. Takes made from files, and those already kept, are recorded. A move is checked against the state it was read in, so two people stopping one take at once cannot overwrite each other: the second is told the take changed.
- **Wall clock.** Rolling and stopping are timed by the server's clock unless the log gives the times itself (as one written offline will). The recorder's timecode in and out are kept as written.
- **Numbering, per session.** *Continuous* runs on from the project's last take, whichever track it was of, so every take of a recording has its own number, as a classical session counts them; *per track* runs on from the track's last take; *recorder* takes the recorder's number as given, refused when that number is already logged for the track. Numbers stay unique per track: continuous numbers are above every number in the project, and every way a take gets a number (logged live, made from a file, imported) waits on one advisory lock per project, so two takes numbered at once on different tracks never share one.
- **Session.** A session says how it numbers and the slot it is booked for, which the take log counts down to. A take logged in a session for a track it did not name adds the track to it.
- **More of a take.** False starts, the page a take ends on (beside the page it starts on and its bars; never without the first, nor before it), and both timecodes.
- **Export.** The log as CSV is built in the browser from the session the page already holds, like the task list's; notes and names are never read as formulas.

Several people at once with their own views, local-first writes, the session clock and the tone and metronome follow in the next parts.

## 150. The take log is a session's page, kept by keys, read from the clock

#51, second part. Each session has a take log at `/sessions/:id/log`, opened from the session's page: the prototype's take log is the log of one session too.

- **Keys.** Space starts the next take, or stops the one rolling (an armed take rolls); A arms the next; X aborts the take rolling or armed; F counts a false start, 1 to 5 rate, S stars and N writes a note, each on the take rolling or, between takes, the last one logged. A session the recorder numbers asks for the recorder's take number beside the track, and starts nothing without one.
- **One live take.** A session has at most one take armed or rolling. Two people starting at once, the server refuses the second under the numbering lock and says which take is rolling; the log shows why.
- **Clocks.** The take's time, the slot's countdown and the wall clock are worked out from the clock whenever they are shown, never counted up, so a laptop that sleeps through a take shows its true length when it wakes. Under ten minutes left, the countdown turns to the signal colour.

The log is read again every two seconds, so a take one person starts the others see; the producer's score and notes, the engineer's patch, and pushing changes to everyone at once follow in the next part.

The note field takes up someone else's change to the note unless it is being typed in, so it never writes an old note back over theirs. While the server cannot be reached the log says so plainly and logs nothing; writing offline and syncing later is the part after.

## 152. The take log's tuning tone and metronome

#51, fourth part. Beside the take log, in every view, a tuning tone and a metronome, as the prototype has.

- **On this device only.** Each is played by the page in the browser (Web Audio) for whoever has it open; nothing is stored on the session or sent to the room, as a tuning fork and a click are personal tools.
- **The tone.** A sine at 415, 432, 440 or 442 Hz, the pitches rooms tune to; pressed, it sounds until pressed again or another is chosen, fading in and out so it never clicks.
- **The metronome.** A short click on every beat, from 30 to 300 a minute. The beats are timed on the audio clock and scheduled a moment ahead, so a busy page does not make the click drift. The last tempo is remembered on the device.
- **The output.** Where the browser lets a page play to a chosen output (Chrome and Edge do), a list chooses where the tone and click play, such as headphones while the room monitors stay on the desk. Such a browser names its outputs only to a page it trusts with a microphone, so the list appears once it has; where the browser can ask the person for an output itself, "Choose an output" does. The log never asks for the microphone just to list speakers. Elsewhere the tone and click play through the default output.
- **Steady under load.** Beats the scheduler missed (a busy page, a tab in the background) are skipped rather than played late, so the click never bursts and stays on the beat.

The recorder's numbers and timecode wait for the session tools; local-first writes and the large-print overview follow.

## 154. The take log, ready to be written offline

#51, sixth part: the server half of writing the take log offline and syncing it later. The browser half (keeping writes while the connection is down and sending them when it returns) follows.

- **A take made once.** The take log may give a take its own id (a UUIDv7, as every id is). A start sent again, because the log could not tell whether the first arrived, returns the take it made rather than a second one. An id another session or workspace already holds is refused.

- **Conflicts per field, with history.** A change sets only the fields it names, so two people changing different fields both stand. On the same field the later write stands. Every field a change sets is kept in the take's history (`take_changes`): what it replaced, what it became, who wrote it and when, by their clock and by the server's. A change that carries what its writer last saw of a field, and finds something else there, is marked as having overwritten someone else's change, so the history shows the conflict and the overwritten value can be put back.

## 155. The take log, written offline

#51, seventh part: the browser half of decision 154. The take log is written here first and sent when it can be.

- **Every write through the outbox.** Starting a take, stopping it, a rating, a star, a false start, a note: each is kept in this browser (IndexedDB, so it survives a reload or a laptop closed mid-session) and shown at once, then sent in the order it was made. - **Refused.** A write the server refuses for what it is (another take already rolling, a stop someone else made first) is let go, and the log says why. A change that replaces someone else's change to the same field stands, and the take's history keeps both (decision 154).

## 157. Score marks belong to the track

#52, first part: the score marks and the edit plot check, on the server. The score marking page follows.

- **On the track, not the file.** A score mark (docs/domain.md) is kept on its track and placed by page, by a point on the page (0 to 1 across and down, a region's corner and size for an issue) and by bar where known. Swapping the score for a new edition keeps every mark where it was.

The edit plot check reads the track's edit points in reading order and says where the chain breaks: a hand-over from a take the plot is not in, a second lead-in, no lead-in, or a take never recorded for the track.

Those who use the production tools add, rename, recolour, re-key and remove them; no two share a name or a key, and an issue whose category is removed keeps everything else.

- **Who may.** Those who see the production tools see the marks; those who use them make, change and rub them out.

## 161. Going to a bar by the numbers the score prints

#52, fifth part: "go to bar via the score's text layer".

- **Read once, as the score is drawn.** When a PDF's pages are drawn, its text is read for the whole numbers in it and where they sit (`pdftotext -bbox`). The bar numbers among them are the longest run that rises through the score in reading order, the earliest such where there are several, after leaving out large type (titles, headings) and the top and foot margins (page numbers). Fingerings, tuplets and rehearsal figures rise and fall, so they drop out; and since a run of fingerings can rise too, the number at the start of each system (the first on its line, near the page's left edge) is preferred, with every number read only for a score that numbers its bars along the systems instead. Fewer than three is not trusted. The file keeps them (`files.printed_bars`), and the score's view returns them with its pages: numbers and places only, nothing else of the text. A score drawn before this has none until it is drawn again.
- **Go to bar.** Beside Go to page, as the prototype has it. The score turns to the page of the last number at or before the bar, and marks that system for a moment with a hairline in the signal colour. It says where it went, so a screen reader hears it too ("Bar 21, page 2"), and between two numbers which system the bar is in ("Bar 23 is in the system from bar 21"). A scanned score, with no text, goes by the bars its marks name, and says when it has nothing to go by.
- **Not a bar map.** This finds a bar on the score; it does not tie the score to a recording (decision 034 stands).

## 162. Swapping a score keeps every mark on its bar

#52, sixth part: "swap a score file mid-project and keep every mark and link".

- **Marks were never the file's.** Score marks and takes belong to the track (decision 158), so swapping its score (the track's Use … menu) never lost one. What a swap changed was where they sat: a new edition puts the bars elsewhere.
- **They follow their bars.** When a track's score is swapped for another, a mark that names a bar moves to that bar in the new score, by the bar numbers both print (decision 161), and keeps its place above or below its system's number; the whole mark moves by one shift, kept on the page, so a region keeps its height and ink its shape. A take's score pages move the same way, each end by its own bar (the first page by its first bar, the last by its last), never leaving the last before the first; the take's history records each as a change by whoever swapped the score. This happens in the transaction that swaps the score, under the track's lock, and needs only what swapping it needs (organise).
- **A score still being drawn.** A score chosen straight after upload has no bars read yet. The track then remembers which edition its marks sit on, and the marks follow once the new score is drawn; a swap meanwhile starts from that same edition, and a score that cannot be drawn leaves them where they are.
- **What cannot follow, stays.** A mark that names no bar, or a swap to or from a score without printed bars (a scan), leaves things where they were. The track page says what moved and what stayed ("Moved to their bars in the new score: 12 marks and 2 takes. 3 marks stayed where they were, with no bar to find them by.").
- **Links.** Comments on the old score stay on it, as comments belong to their file; bar comments on recordings name bars, not a score, and need nothing.

## 177. Migrations that lose nothing unasked

#154, first part: "`MIGRATE_ON_START` takes an advisory lock so two replicas cannot migrate at once; a migration that would drop or rewrite data refuses to run without `MIGRATE_ALLOW_DESTRUCTIVE`; a pre-flight at start-up compares the schema version with the code".

- **One at a time.** Migrating takes a session advisory lock in PostgreSQL on its one connection and reads what is pending under it, so replicas starting together migrate once: the first applies, the rest wait and find nothing left.
- **Losing data.** A pending migration that drops a table, a column or a type, changes a column's type, truncates or deletes rows is refused, naming each statement, until the operator starts once with `MIGRATE_ALLOW_DESTRUCTIVE=true`. Nothing is applied when one is refused, the harmless ones before it included. A backfill (`UPDATE`) adds data and is not counted. A new, empty database is never refused, though early migrations dropped columns: there is nothing in it to lose.
- **Known.** The migrations that lose data are listed in `packages/db/src/migrate.test.ts`. Adding one fails that test until it is listed, which is the reminder to write its upgrade notes.
- **Pre-flight.** Without `MIGRATE_ON_START`, start-up compares the database with the code: behind, it names the pending migrations and how to apply them; ahead (migrated by a newer release), it refuses whatever the setting, as running would misread the data. Each stops the app before anything is served.
- **Upgrade notes.** A change an operator must act on carries a `BREAKING CHANGE:` footer, which Release Please writes under the release's "⚠ BREAKING CHANGES"; a release pull request may add an "Upgrade notes" section by hand. The docs site's build gathers both from `CHANGELOG.md` into one Upgrade notes page, newest first, and says so when none were needed.
- **Follows.** Maintenance mode, with instance settings (#160).

## 178. Instance settings and maintenance mode

#160, first part, with #154's maintenance mode: "settings live in an `instance_settings` table (global) with a zod schema, and every change is an audit event".

- **One row.** `instance_settings` is global: a setting is the instance's, not a workspace's. Its one row holds the settings as JSON, checked by `instanceSettingsInput` in packages/shared and read over the defaults, so a row written before a setting existed still reads. Every process reads it again within 15 seconds, so a change needs no restart.
- **Every change an event.** Saving records one instance event for each thing that changed (a second factor required or not, maintenance on, off, or a new notice), shown on the Overview's Recently.
- **A second factor for every account.** The switch joins `REQUIRE_SECOND_FACTOR`: either asks it of every account. When the environment sets it, the switch shows on and cannot be turned off.
- **Maintenance mode.** While it is on, every page, signed in or not, shows a notice under which the operator may add a line. Uploads (starting one, its chunks, finishing it, a comment's attachment) are refused with 503 and the files they would send stay with the sender. The job workers stop taking jobs and finish those under way, and the queue keeps the rest until it is over. Nothing is lost.
- **What the environment sets.** Shown beside them, read-only: operators' security keys, session length, password rules, the address and instance mail.
- **Follows.** Defaults for new workspaces (storage, members, guest links, forensic marking) with quotas (#175) and marking (#32); workspace subdomains (#176); mail channels and a test (#161); telemetry (#162); modules with billing (#178) and support (#181).

## 179. System information

#158, as decided there: "for 1.0 the page shows versions and available releases only; the image stays immutable". Hot patches would be a later, opt-in feature of their own.

- **What runs.** The release (the server package's version, which Release Please sets) and the build: the commit the image was built from, passed in as `HEKATE_BUILD` by the release workflow, or "a development build". Each release the instance starts is noted once, for the History.
- **Releases.** With `HEKATE_UPDATE_CHECK=true`, a job reads the project's public releases feed once a day (and on *Check now*); nothing about the instance is sent. Off by default, the instance asks nothing of anyone. Drafts and tags that are not versions are left out; a failed check is kept beside the releases the last good one found, so the page says why it is behind.

## 180. Liveness and readiness

#156, first part: "`/api/health/live` (the process answers) and `/api/health/ready` (database, storage backends, worker, mail reachable), for Compose, Kubernetes and the Dockerfile's HEALTHCHECK".

- **Live.** The process answers: nothing more is checked, so a slow database never gets a healthy process restarted.
- **Ready.** Ready to serve when the database answers and every storage backend can be written to; not ready otherwise, and while the installer runs. The worker (a job finished in the last ten minutes) and mail (the SMTP server answers) are reported beside them but never make a replica unready: taking every replica out of a load balancer for want of mail would only make things worse (`readiness` in packages/shared).
- **Public, so states only.** The answers name no host, bucket or address, only `ok`, `failed`, `stale` or `off` for each part.
- **Kept ten seconds.** A storage check writes a probe, so a readiness answer is kept that long rather than written for every probe.
- **`/api/health`** stays as it was for the image's `HEALTHCHECK`.
- **Follows.** The System health page: gauges, the last 24 hours, services and storage (#156, later parts).

## 181. System health

#156, second part: "The System health page: Now (CPU, memory, disk, database connections as gauges), the last 24 hours (requests per minute, p95 latency, error rate, queue depth, worker lanes busy, uploads) as sparklines … services … The metrics catalogue … Done when the page reads from `/metrics` data kept in PostgreSQL for a day".

- **A minute a row.** Each process writes one row a minute to `health_samples` (global; a replica is a random id, never its host), and deletes rows a day old as it does. The counts are the differences between two readings of the registry's own counters, and the p95 is worked out from the histogram's buckets as `histogram_quantile` does, so each chart shows what the metric it names would.
- **Every replica together.** Requests, errors, lanes and uploads add up across replicas; the p95 is the slowest replica's, and queue depth (read from the shared queue) is the same for all.
- **Points.** The hour is a point a minute, the day a point a quarter of an hour, rates per minute measured (`healthSeries` in packages/shared). A point no process measured is a gap, not a zero. The prototype's "Last 7 days" went: a day is kept.
- **Now** is the answering process's machine: processors over its last minute, memory, the disk holding local storage (or the working directory) and the database's connections.
- **Services** are the readiness checks (decision 180) with what explains them. The prototype's Proxy went (Hekate cannot see Caddy from inside), and so did the worker's Start button: the worker runs in the app's process, so a stopped one is a restarted container. The billing gateway's row follows billing.
- **Worker lanes** are new metrics: `hekate_worker_lanes` (jobs a process may run at once) and `hekate_worker_lanes_busy`.
- **Metrics** lists the registry itself, with each metric's help, so the catalogue cannot drift from what is exported.
- **Follows.** Storage backends with usage, the master key and reconciliation (#156, last part).

## 182. System health: storage

#156, last part: "storage backends with usage, the master key with its rotation date, reconciliation with \"run a slice now\"".

- **Backends.** Each configured backend with where it keeps objects (path, or bucket and region), whether it takes new objects, the bytes stored there, and whether it answers now. A local backend also shows its disk filling; S3 has no size to fill, so it shows none.
- **The master key** lives in the environment, so the page cannot rotate it: it says how many workspace keys it wraps, warns while earlier keys are still configured, and links to the rotation steps in the docs. The prototype's rotation date went: nothing records when an operator changed the environment.
- **Reconciliation** runs over everything each night, not a slice at a time, so the prototype's "Run a slice now" became "Run now": it queues the same job (one at a time, three a quarter of an hour), recorded in the instance's events. The row says when the last instance-wide run finished and what is still open.

## 185. Logs as tables: audit and mail first

#157, first part.

- **Audit** reads what is already written, not a new table: the operators' instance events, and each workspace's access log less streams and page renders (which stay in the workspace's own log, as on the instance's workspace page). An operator's event about a workspace (its id in the details) counts as that workspace's when filtered.
- **Mail** gains a writer: every message handed to instance mail is written to `mail_events` (global: a message may concern no workspace) as sent, refused with the mail server's words (kept to 500 characters), or written to the log where there is no SMTP. Writing it never holds up the message nor hides its failure.
- **Reading.** Newest first a page at a time, by id: ids are UUIDv7, so a range is a scan of the primary key. Search, a range of an hour to thirty days, and a workspace (audit).
- **Export** streams the whole filtered log as CSV, its cells neutralised as the access log's; it is an instance event (`logs.export`) written before any of it leaves.
- **Follows.** Authentication, with writers for sign-ins, refusals, lockouts, second factors and guest links; then retention per kind as a job, and the live tail. API, webhooks and the billing gateway arrive with their features. The prototype's Email tab loses its Template and Provider columns: a message knows its subject, not its template.

## 186. The authentication log

#157, second part.

- **One writer for every sign-in.** A session made by a sign-in path is the sign-in: password, passkey, a second factor, the workspace's directory or its single sign-on (`signInMethodOf`), recorded from the session Better Auth just made, with its workspace where the session names one. A password that waits for its second factor is not yet a sign-in; the second factor's is. Refusals are recorded with Better Auth's reason, a lockout as locked, and a try made to wait as refused for too many attempts.
- **Guests too:** a link opened (or one that opens nothing), a code right or wrong, each with the guest's workspace.
- **Global** (`auth_events`, in `globalTables` like error reports): a member's sign-in belongs to their account, not a workspace. Where a workspace is known it is kept, and goes with the workspace.
- **The address** is read as the access log reads it: X-Forwarded-For's last entry behind Caddy (TRUST_PROXY), none otherwise, as a client could claim any.
- **Beside, never awaited**: a slow or failed write holds no sign-in up.
- **Forgetting.** Deleting an account rewrites its address to "A former member" here and in the mail log, as the access log and the instance's events already do.
