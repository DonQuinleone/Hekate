# Media security

Material in Hekate is unreleased. It is shared with many people before the public ever hears or sees it. Protecting it is a core requirement, designed in from the start, not a later feature.

Two goals:

1. **Stop casual extraction.** Nobody should be able to open the browser's developer tools and save a usable copy of an audio file, video, score or artwork.
2. **Make leaks attributable.** If something reaches the public, we can tell whose access it came from.

Anything that can be heard or seen can be recorded from the speakers or the screen. Hekate does not pretend otherwise. It removes the easy routes and makes the hard routes traceable.

## Principles

- **Originals never reach a browser by default.** Reviewers get protected derivatives. Downloading an original is a separate permission, and every download is logged and watermarked. A download is a link that works once, for five minutes, in the session that asked for it, and is logged before its first byte leaves (decision 056).
- **No plain media URLs.** There is no URL that returns a whole file to anyone who holds it. Everything goes through short-lived, signed, session-bound delivery.
- **One public object: a workspace's logo** (#185, decision 226). It is shown before anyone signs in (a workspace's sign-in page, its mail), so it is served to anyone, at `/api/branding/<workspace>/logo/<id>`. It is never what was uploaded: only PNG, JPEG and WebP are taken (by their first bytes, never SVG), each opened by ffmpeg with that one demuxer and only from a file, refused past 8192 pixels a side before it is decoded, and drawn again as a fresh PNG of at most 512 pixels with no metadata, which is all that is kept, encrypted like any other object. The address answers only for the blob the workspace's branding names as its logo, and changes with every new one, so it can be cached for good; it carries its own policy (`default-src 'none'; sandbox`), `nosniff`, and is the only response allowed across origins (`Cross-Origin-Resource-Policy: cross-origin`), for mail clients. Every reader of a mail loads the same address, so it tells nothing about who opened what.
- **Encrypted at rest.** Stored files are encrypted with a per-file key.
- **Every access is logged.** Keys issued, segments served, pages rendered and downloads, with the person or guest and the review they came through.

## Authentication

Members sign in with what their workspace already uses; guests never need an account.

- **Operators:** the instance side is open to its operators and, for their own workspaces only, to workspace owners; the server checks which on every request (decision 062). Operators are accounts in a global table, the first made by setup; an operator acts only from a session signed in with a passkey or hardware security key (`OPERATOR_SECURITY_KEY`), and the last one cannot be removed. What operators do is written to the instance's own event log. An operator may suspend a workspace with a reason: every member route, play link and guest session then refuses it (403, `workspace_suspended`) until it is reinstated, and nothing in it is deleted. Operators never sign in as a member; for someone locked out they can send a password reset, remove the code app and passkeys so they enrol again, or end every session, and each is logged (decision 063). Only a suspended workspace can be deleted, and its rows and stored objects are purged thirty days later (its owners can delete it too, two of them agreeing, which suspends it for the same thirty days; see Workspace export and deletion below); an operator can rotate a workspace's key, after which every data key, rendition key and sealed secret is rewrapped in the background and earlier versions are kept for backups (decision 064).
- **Installing:** a server without a database or a master key starts as an installer and serves nothing else (decision 061). Every installer request, and creating the first owner, needs the setup code the server prints in its log at start: twelve characters from an alphabet without look-alikes, made anew at each start (`HEKATE_SETUP_CODE` fixes it for tests), compared in constant time, and refused after ten wrong tries in ten minutes. The code is only good until an owner exists. What the installer is given (the master key and mail password among it) goes into a settings file written whole and readable by the server alone, on a volume apart from the media; the environment wins over it. The master key is made in the browser, never sent to anything but this server, and is saved only once the person says it is stored elsewhere.

- **Single sign-on:** one identity provider per workspace, by OpenID Connect (with PKCE) or SAML 2.0 (signed assertions required, each accepted once), set by its admins (Settings, Security) on Better Auth's SSO plugin. The person names the workspace, or the workspace's own host does (#176); the provider is found by workspace, never by the domain of an address. The first sign-in makes the account and the membership; every sign-in sets the role the groups give (named groups make admins, everyone else is a member, owners stay owners), and is logged. An address that already has an account here is refused rather than linked, so a provider can vouch only for people it brought. Saving an OIDC issuer reads its discovery document once; the server fetches only from public addresses, or from origins the operator lists in `SSO_TRUSTED_ORIGINS` for a provider on a private network. The OIDC client secret is kept in the database as Better Auth needs it to sign in, and never sent back. A workspace can enforce single sign-on: every member route and play link then refuses a member whose session did not come through it (403, `sso_required`); owners keep their password, so a broken provider never locks a workspace out. A second factor the workspace asks for is still asked for, because Hekate cannot see what the provider checked (decision 050).
- **Directory:** LDAP (including Active Directory), per workspace (Settings, Security). The person types the workspace's short name, their directory username and password; Hekate searches as a service account (or anonymously), binds as the person to check the password, and reads their address, name and groups. The first sign-in makes the account and the membership; every sign-in sets the role the groups give (named groups make admins, everyone else is a member, owners stay owners), and is logged. The username is escaped before it enters the search filter (RFC 4515), and wrong passwords are slowed and locked as passwords are. A directory vouches for its own workspace only: an address that already has an account here, not made through that directory, is refused rather than taken over. `ldaps://` verifies the certificate unless an admin turns that off; the service account's password is sealed with the workspace key (AES-256-GCM) and never sent back. The sign-in page offers the directory only while some workspace has one turned on (decision 049).
- **Passkeys and hardware security keys:** WebAuthn passkeys for passwordless sign-in, and hardware security keys such as YubiKeys, for this instance's address only. A key signs in on its own, or confirms a password sign-in where a second factor or a hardware security key is asked for. Five keys per account by default (`MAX_PASSKEYS` raises it), each named, with when it was last used, and individually revocable; adding and removing one is logged. Recovery when every key is lost is the code app's recovery codes, or a new password by email.
- **Passwords:** optional, can be disabled per workspace; always paired with a second factor when policy requires. Twelve characters at least, and checked against known breaches (Have I Been Pwned, sending only the first five characters of a hash; `PASSWORD_LEAK_CHECK=false` turns it off on an instance without internet access).
- **Guessing:** per account, the first four wrong passwords cost nothing; after them each try waits twice as long as the last, up to a minute; ten within a quarter of an hour lock the account for a quarter of an hour, written to the access log of each workspace it belongs to. Attempts are kept under a hash of the address, never the address. A per-address limit also stands in front of every sign-in.
- **Forgotten passwords:** a six-digit code by email, with a link that carries it; both last ten minutes, work once, allow three tries, and are stored hashed. Setting the new password ends every session the account has, and is logged. Asking for a code says the same whether or not the address has an account. Members are never signed in by an emailed link or code (decision 025).
- **Guests:** magic links. A guest receives a single-use, short-lived link by email, scoped to the reviews they are invited to; opening it starts a session bound to that browser. Links last three days unless a workspace admin chooses 14 or 30 (Settings, General; the longer the life, the longer a forwarded or intercepted mail stays useful, so three is the default), are stored only as hashes, and sending a new one revokes the last. The session lasts a fortnight in an httpOnly, SameSite Strict cookie. Links can be re-sent and revoked, and every use is logged. A workspace can also ask for a code (Settings, General, "Guests sign in with"): opening the link then signs no one in, but sends a six-digit code to the address the review was sent to, so a forwarded mail is no use to whoever it was forwarded to. The code lasts ten minutes, allows five tries, is stored only as a hash bound to its link, and another can be sent after half a minute, five in all per link; the link is spent only when the code is right. Each code sent and each failed try (wrong, expired, too many) is in the access log.
- **Sign-up:** closed unless an operator opens it (Settings, Registration; decision 219). Better Auth's own sign-up route is always refused; workspaces made without an operator go through `/api/sign-up`, and only as registration allows: invite-only takes an operator's invitation, open takes any email that confirms itself. Every way in is a link mailed to the address (a day for one asked for, a week for an invitation), a 256-bit token kept only as a hash, removed in the same transaction that makes the workspace, so it works once; asking for one says the same whether or not the address has an account. An address with an account must be signed in as it to use its link. A new password is twelve characters or more and checked against known breaches. Links asked for are limited by address and by email, and workspaces made by address and by email (429 with Retry-After). Each workspace made is an instance event, and each invitation sent or withdrawn too. Closing registration stops every link still waiting.
- **Second factor:** a code app (TOTP: six digits, every 30 seconds) asked for after the password. Adding one asks for the password again, shows the key as a QR code and as text, and takes effect only once a first code from it is right. Ten recovery codes are issued then and shown once; each works once, and they are stored only as keyed hashes (HMAC-SHA256 with the auth secret), never as codes. The code app's key is stored encrypted with the auth secret. A browser can be trusted for 30 days, so it is not asked there again. Ten wrong codes in a row lock the second step for a quarter of an hour. Removing the factor, or generating new recovery codes (which replace the old), asks for the password; adding, removing and new codes are written to the access log of each workspace the account belongs to.
- **Policy:** per workspace, admins choose whether a second factor is required of nobody, of owners and admins, or of everyone; nobody can require one they do not have themselves. `REQUIRE_SECOND_FACTOR=true` requires it of every account on the instance. Someone who owes one is asked at their next request, wherever they are, and every member route refuses them (403, `second_factor_required`) until they add one; they may still read who they are and switch to another workspace. Operators always need a hardware security key (decision 039). A workspace can also require owners and admins to sign in with a passkey or hardware security key. Each session records how it was signed in (decision 048), and the rule reads the session: someone with a key who signed in with a password is asked to confirm with it, and only someone with no factor is asked to add one. Enforcing single sign-on is the one choice of method so far; choosing each allowed method is not built yet.

## Delivery

### Audio and video

- The media worker produces segmented proxies (HLS with fragmented MP4 segments) for every audio and video file, once the file has been measured. Audio gets a stereo AAC rendition for quick listening, a lossless FLAC rendition at the source's rate, bit depth and channels (a browser plays up to eight from one stream, so a wider layout such as 7.1.4 is carried in parts of up to eight, in its own order, each an encrypted rendition with its own key; the player plays them in step and hears them as one) and, for Dolby Digital and Dolby Digital Plus sources (including E-AC-3 carrying Atmos), the original stream passed through untouched. Video gets an H.264 ladder of up to two rungs at or below the source size.
- An ADM master with objects is first rendered to a loudspeaker layout by the EBU ADM Renderer, a Python program run as its own process like ffmpeg, in the same private workspace; it opens no connection and writes only its render there (decision 140).
- ffmpeg packages the renditions in the job's private workspace. Hekate then encrypts each segment and the initialisation section with AES-128-CBC (the HLS `AES-128` method) under a random content key per rendition, with a fresh random IV for every segment, and stores the ciphertext as ordinary encrypted blobs. The content key is stored wrapped by the workspace key, like a data key. Plaintext segments are deleted from the workspace as they are sealed.
- Playback starts with `POST /api/files/:id/playback`, which needs membership of the file's workspace and returns a playlist URL carrying a signed token. The token names one file, is bound to the viewer's sign-in session and expires after four hours. Every playlist, segment and key request needs both the token and that session's cookie, and current membership; a copied URL is useless on its own, and signing out ends it.
- The key endpoint returns the content key only on a valid token and session. Keys are never cached, are limited to 30 requests a minute per session, and every issue is logged (`stream.key`) before the key leaves. Starting playback (`stream.session`) and every segment served (`stream.segment`, with its rendition and index) are logged too, so the log shows which parts of a file reached whom. All playback responses are `no-store` and same-origin. No CDN or shared cache stands in front of them: one would serve segments without the session check, the access log or immediate revocation, so Hekate scales by adding replicas instead (decision 196).
- The player (hls.js under Hekate's own controls, for audio as well as video) decrypts through Media Source Extensions; Safari on iOS, which lacks them, plays the same encrypted stream natively. The network panel shows only encrypted fragments.
- A video's filmstrip (twelve frames along it, 90 pixels high, side by side in one picture) is made from the same copy as its streams and stored as an encrypted blob on the file. It reaches a browser only through the playback token, like the streams, with the viewer's mark burned into each frame where the project marks them, as a page's thumbnails carry it; like those thumbnails it is not logged apart from the playback session it belongs to (decision 145).
- Waveforms are drawn from precomputed peaks, so the waveform never needs the audio itself. Peaks are each channel's lowest and highest sample over blocks of at least 256 samples, in 8 bits: enough to draw at any zoom, far too little to rebuild audio. They are stored encrypted like everything else and served to members of the file's workspace without a playback token or an access-log entry.
- Loudness and levels are treated in the same way. They are momentary and short-term loudness, each channel's peak and RMS, the phase correlation, mid and side levels and stereo field (the share of energy in each of 16 directions, with no timing within the frame) of the front pair, and the correlation of every pair of channels for recordings of up to eight, one set of numbers every 100 ms. They are measured from the same decode as the peaks, no audio can be rebuilt from them, and they are served like the peaks.
- Spectrograms are treated in the same way. Each channel (and the mid and side of the front pair) has one: the loudest level of every frequency band (about 23 Hz wide up to 24 kHz) over spans of at least 100 ms, in 8 bits, with no phase. A span pools several overlapping analysis windows (at least four, whatever window, FFT size and overlap a viewer chooses), so what is stored is not a short-time Fourier transform, and phase-retrieval methods that rebuild audio from one have nothing consistent to work from. A viewer's own analysis settings (#34) are drawn the same way, by the worker, and kept as their own spectrograms for 30 days after they were last used. That is enough to draw at any colour map, scale and range, but not to rebuild audio. The worker builds them on a separate thread from its own decode of the file in the job's workspace, and their size is bounded however long the file turns out to be.

This is not DRM: a determined person can capture the key from a live session. That capture is tied to their session in the audit log; streams do not carry the forensic mark below yet, which would identify them too. A pluggable commercial DRM (Widevine, FairPlay, PlayReady) can be added later on the same encrypted segments if a deployment needs it.

### Documents and images

- Scores, PDFs and artwork are rendered on the server into page or image tiles at review resolution. The raw PDF or image is not sent to reviewers.
- Tiles are delivered like segments: signed, short-lived, session-bound.
- Tiles for guests carry a visible watermark burned in on the server.
- Text needed for search or bar mapping is extracted on the server; it is not exposed as a selectable layer to guests.

### Comment attachments

- A file attached to a comment (#133, decision 069) is stored as an encrypted blob like any other, with its own data key; storage never holds it in the clear.
- It reaches a browser only as a download: a one-time link made for the person asking, in their session, for five minutes, as for a file's downloads (decision 056). The comment is checked again as the link is made and as it is used: it must be among the threads the file shows that person, within a guest's scope. The download is in the access log (`comment.attachment_download`) before the first byte leaves, and is sent as an attachment, `no-store`, `nosniff`, never shown in the page.
- Only a comment's author attaches to it (up to five files of 25 MB each), and only they remove them; adding one is logged (`comment.attachment_add`). Attachments are not watermarked: they are the reviewers' own material, not the media under review.

### Caption tracks

- A caption track's sidecar (#146, #201, decisions 144 and 235) is an encrypted blob like any other, kept as it came and never sent back. Its cues (the words and their times) are in the database, scoped by workspace, and reach whoever may view the file, as its comments do.
- An export is written afresh from the cues as SubRip, WebVTT or TTML, for whoever may download from the file at either level (or through a review that allows downloads), in their session; an API token needs the `downloads` scope. It is in the access log (`file.captions_export`, with the format) before it is sent, as an attachment, `no-store`. Not watermarked: text carries no mark. Adding, changing and removing a track are logged too.
- Hekate transcribes nothing: no media is sent to a speech service.

### Workspace export and deletion

A workspace's owners, and the instance's operators, can take away everything it holds (#186, decision 220). It is the one way originals leave unwatermarked, so it is held to the rest of this page in every other way.

- **Owners and operators only.** The workspace's owners ask for it in Settings; an operator, signed in with a security key, from the workspace's Keys tab. Admins, members and guests cannot, and no one reaches another workspace's exports: every read and link is held to the workspace the session acts in, or the one the operator names.
- **Encrypted to a key shown once.** The archive is a tar file encrypted with age (X25519, ChaCha20-Poly1305), to the person's own age public key or to a key made for it whose secret is returned once in the response that starts it and kept nowhere: not in the database, not in a log, not in the job. The server cannot open the archive it made. Only the public key is stored, on the export's row.
- **No plaintext stored.** Records are read a table at a time and files through decryption, straight into the tar stream, which is encrypted with age before anything is written; the age file is then stored as ordinary encrypted blobs with their own data keys, in parts of at most 64 GiB. Wrapped keys, sealed secrets and the hashes of links and codes are left out of the records, and so are keys, live sessions and downloads, and uploads under way: a test fails on any new column that looks like one.
- **Delivered through the protected path.** A ready archive downloads through a one-time link made for the session that asks, which works once, for five minutes, as a file's downloads do; it is sent as an attachment, `no-store`, `nosniff`. The access log records the request (`organisation.export_request`) and each download (`organisation.export_download`) before the first byte leaves, an operator as themselves marked as an operator, and the instance's events record an operator's too. Not watermarked: it is the workspace's own material going back to it, not material under review.
- **Kept a week.** The archive is removed seven days after it is made, one export at a time per workspace.
- **Deleting takes two owners,** as a project's deletion does (#240): one asks, another confirms by typing the workspace's name, a sole owner a day after asking. Confirmed, the workspace is suspended at once for every member and guest, with its owners still able to keep it or export it, and it is purged thirty days later as an operator's deletion is: every row it owns (its keys, exports and access log among them, the log through its explicit purge), every object under its prefix in every backend, and its keys held in memory.

### Takes shared on a thread

- A take shared on a thread (#133, decision 072) is heard by everyone who sees the thread, a guest reviewer included, and is otherwise no different from any file: the same encrypted segments, short-lived signed URLs and session-bound keys, with every key in the access log.
- A guest reaches a shared take only through a thread their review shows them: on a file of their review, or carried to one, and within their comment scope. They reach it as they reach that file, within the same window and play limit, but to listen only: no comment, no download, and none of the take's own comments, their own from an earlier review included, while a share is all that reaches it.
- Only those who triage the thread's file and may see the project's takes share or unshare one, from takes of the same project. Both are in the access log (`comment.takes_share`, `comment.takes_unshare`), and unsharing closes the take to the guest at once.

### Listening rooms

- A listening room (#200, decision 234) carries only where its leader is: a file's id, playing or paused, a position and a speed. No playback token, segment address or key passes from the leader to a listener; each listener's page asks for its own playback of that file, on its own session, so their permissions, watermark and access log apply as they would to the file opened by hand.
- A room is reached on a member's session alone (never an API token or a guest link), only by members who can see its project in its workspace; someone taken off the project is let go within fifteen seconds. Only the leader moves or ends it, and only to files of the room's project that they can see.

## Watermarking

### Visible

A per-viewer overlay (name or email, workspace, date) on video, documents and images. For documents and images it is burned into the tiles; for video it is an overlay layer in the player. It deters casual screen capture and makes any captured copy self-identifying.

A download carries it too, for whoever asked, whatever the project marks on screen (decision 080). A picture's proxy is the picture as reviewed and its original the picture at full size, in its own format where one can be written, with the mark drawn on. A document leaves as a PDF made of marked page pictures: its pages as reviewed, or, as its original, each page drawn again from the original PDF at print resolution and its own size. A track's score may be asked for with its score marks drawn over the pages, as vectors, by those who may also see the production tools (decision 160), and every score of a project at once, each checked and logged as its own download (decision 163). Neither holds the stored file's text or anything else from it; the marking happens in a private workspace, page by page as the PDF is sent, and is gone when the download ends. A video's download has the mark burned into every frame, encoded as it is sent (decision 081): the stream's largest encode for the proxy, the original at its own size, encoded again, for the original.

### Forensic

Invisible marks that survive re-encoding, so a leaked copy can be traced.

- **Downloads of recordings (built, decision 239).** Each download of a recording, original or proxy, is made on demand with an inaudible mark of its own: small gains (5 per cent) on the spectrum between 400 Hz and 4.6 kHz, in a pattern that follows from the workspace's key and a random mark id, and from nothing else. The mark is written down (`forensic_marks`) with the download's entry in the access log before it is made: who it is for, what of, through which review. The marking happens in a private workspace, removed when the download ends; nothing marked is stored. The original keeps its own format where it is PCM in WAV or AIFF, or FLAC (a WAV original is its own file with the marked samples in place, every other chunk untouched); other originals leave as FLAC; the proxy is AAC at 256 kb/s. It is off until a workspace's owners turn it on; the plans' `forensicMarking` feature includes it.
- **The key.** The pattern's key is derived one way (HKDF) from the version of the workspace's key current when the mark was made, so it lives only in memory, under the same hierarchy as the data keys, and reveals nothing of the key that encrypts files. Each mark records the version; earlier versions stay, as rotation keeps them.
- **Detection (built for recordings).** An owner uploads a suspected leak under Workspace settings, Leak tracing. Its first ten minutes are decoded in a private workspace, compared with every mark the workspace made, and the file is removed. A match is reported only when the chance of a mistake, bounded and counted over every comparison made, is below one in a million; it names the download, and the trace itself is in the access log (`forensic.trace`) whatever it found. What survives, and what does not, was measured and is in decision 239: lossy encoding down to 96 kb/s and resampling, yes; a change of speed of one per cent, no; recording through the air, not tested.
- **Not yet.** Streams (A/B segment marking: two marked variants of each segment, each recipient served a unique sequence), video, pictures and PDF pages carry only the visible mark. Each needs a decision of the owner's first (#32).

## Encryption at rest

Envelope encryption: every stored object (an original or a derivative) has its own random data key; data keys are wrapped by a workspace key, which is wrapped by an instance master key. Storage backends (local disk or S3) only ever hold ciphertext. Rotating the master key re-wraps workspace keys without touching files.

- **Objects** are encrypted with AES-256-GCM in 64 KiB segments, following the STREAM construction (as in Tink and age). Each nonce is a random 7-byte prefix stored in the object's header, the 32-bit segment index and a final-segment flag, so segments cannot be altered, reordered, dropped or truncated undetected. The blob's id is bound as associated data, so ciphertext cannot be moved between objects. Segments make byte ranges cheap: a seek in a long recording decrypts only the segments it touches.
- **Data keys** are wrapped with AES-256-GCM by the workspace key, bound to the blob's id, and stored on the blob row.
- **Workspace keys** (`organisation_keys`) are created on first use, versioned for later rotation, wrapped by the master key and bound to the workspace and version. Unwrapped keys exist only in the server's memory.
- **The master key** comes from `MASTER_KEY` (or `MASTER_KEY_FILE`). Each wrapped workspace key records a one-way fingerprint of the master key that wraps it. At start-up Hekate checks every workspace key against the configured master keys and refuses to start if one cannot be opened, rather than failing on the first read.
- **Rotation:** move the current key to `MASTER_KEYS_PREVIOUS`, set a new `MASTER_KEY` and restart. Hekate re-wraps every workspace key with the new key at start-up; the old key can then be removed. Stored objects are never rewritten.
- **Key management services** (AWS KMS, Vault and so on) can replace the configured master key later behind the same interface.

## Storage reconciliation

A daily job compares every storage backend with the database, one workspace at a time.

- **Orphaned bytes** (objects no blob row accounts for, including those of a deleted workspace) and **unused blobs** (no file, rendition, segment, peak level, loudness series, spectrogram or unfinished upload points at them) are recorded on first sight and removed only when a run at least a day later still finds them. Uploads and jobs in flight are therefore never touched. Each removal is written to the workspace's access log (`storage.remove`).
- **Missing bytes** (a blob row whose object is gone) mean data loss. They are reported (logged, and `storage.missing` in the access log once) and never changed: a person decides.
- `STORAGE_RECONCILE=report` keeps the findings and removes nothing.

## Uploads

Uploads are resumable and never sit on the server as plaintext.

- The browser creates an upload, then sends 8 MiB chunks in any order, three at a time, each with a SHA-256 `Content-Digest`; damaged or failed chunks are re-sent. Choosing the same file again after a dropped connection resumes from the chunks already received.
- Each chunk is encrypted the moment it arrives (128 segments of the format above, under the upload's own data key and nonce prefix) and stored as one part of a multipart upload in the chosen backend. The encrypted chunks join into exactly the object a single stream would have produced.
- Completing an upload creates the blob and the file, records a `file.upload` event, and queues the checksum and probe jobs. The checksum job reads the file back through decryption, which also proves it is intact.
- An upload belongs to the member who started it. Unfinished uploads expire after seven days; an hourly job discards their stored parts.

### Upload requests

A link for someone outside a project to send files into one of its folders (#139, decision 199).

- The link is the credential, as a guest's is: 32 random bytes, kept only as a SHA-256 hash, so it is shown once (and mailed, if the requester gives an address); a new link replaces it and the old one stops at once. A wrong, closed, lapsed or replaced link, or one into an archived project or a suspended workspace, gets the same refusal.
- It reads nothing. The visitor's page shows only the request's own words, its workspace's name and how many files have arrived; the link sends files into the request's folder and asks after its own uploads, never a file, a folder or anything else of the project.
- An optional password is kept as salted scrypt and asked for before each file starts; a wrong one is in the access log (`upload_request.password_failed`). Opening links and starting files are rate limited per address.
- Files are uploaded exactly as members' are: chunked, encrypted on arrival, checked as they land. A place is taken under a lock on the request when a file starts, so its file limit holds however many start at once, and a file still being sent counts. The upload is logged with a `visitor` actor named as the sender said, and the requester is told.
- A request to a track (#425, decision 223) is made only for a track of the request's own project and workspace. The file becomes the track's next version on the server, once measured, under the project's version checks, which a visitor cannot ask to be let through; the link still reads nothing of the track.

## Media processing

The media worker runs ffmpeg and ffprobe on uploads, which are untrusted input.

- **No playlists, no network.** Every call allows only the `file` protocol and an allow-list of real media demuxers, so a crafted upload cannot be an HLS playlist, concat list or image sequence that reads other files or reaches the network. Arguments are passed as a list, never through a shell, and file names are prefixed with `file:`.
- **Bounded.** Each run has a time limit, honours cancellation, and caps how much output it keeps.
- **Scratch space.** Media tools need seekable local files, so a job decrypts its input into a private directory (mode 0700) that is removed when the job ends, whether it succeeds or fails. If a worker dies mid-job, the next worker to start removes what it left. The Compose file mounts the scratch space as a tmpfs (`HEKATE_WORK_SIZE`, 8 GB by default), so plaintext never reaches a disk; elsewhere, point `WORK_DIR` at a tmpfs. An imported ControlRoom project file (decision 242), which may hold unreleased scores, is read the same way: written to a private scratch directory for its request alone (the file 0600), read with SQLite read-only, and removed when the request ends; its scores, attachments and stage plan underlays reach storage only through the encrypted path.
- **Tenancy.** Job data carries only a workspace (organisation) id and record ids; workers load everything else themselves, scoped to that workspace.

## Audit

An append-only access log records who accessed what, when, through which review, from which IP address and user agent, and whether it was a stream, a page, a key or a download. Owners can filter it per file, per person and per review.

- **Append-only in the database.** Triggers refuse every update, and every delete or truncate unless the transaction explicitly turns on `hekate.audit_purge`, which only retention and workspace removal do. A bug or a careless query cannot quietly rewrite history.
- **Self-contained records.** Events keep plain ids rather than foreign keys and copy the person's name and email at the time, so the record outlives the files, people and reviews it mentions.
- **Written before access.** Recording is awaited: if an event cannot be written, the key, page or download it describes is not served.
- **Client addresses** come from the socket, or from `X-Forwarded-For` only when `TRUST_PROXY` is set (the Compose file sets it, because Caddy replaces that header with the real client address). A client cannot claim another address otherwise.
- **Reading and export** are for workspace admins and owners: filters by project, file, review, person, action and time, newest first with cursor paging, and a CSV export. Exports are themselves logged, and cells that a spreadsheet would run as formulas are neutralised.

### Error reports

Every failure a person sees (any 5xx) and every job's last failed attempt is recorded under a reference such as `HK-7F3A-2C` (#159), which the message asks them to quote, and written to the log as one JSON line. The report holds the route or the job, the request's id (made by the server, never taken from the request), the error and its stack, the job's data (identifiers only), the workspace, and the account it happened to; nothing else about the person, no address and no browser. Only operators read reports, in Debug tools, where the account is shown by its name and email. A workspace's reports are deleted with it, and every report after 30 days. Debug tools' inspectors show an operator a file's, a review's or a session's records, never stored content, and each look is written to the instance's events (decision 066).

## Channels and webhooks

A workspace's events can go to Slack, Discord, Microsoft Teams or a webhook of its own (#161, Settings, Notifications and integrations; admins only).

- **What leaves.** An event names things (the workspace, project, review, track or file, and who acted) and links to them in the app. It never carries media, a link to media, a comment's words, a decision's note, or who was mentioned; the schemas are in `packages/shared/src/events.ts`.
- **Addresses sealed.** A channel's address, which for Slack, Discord and Teams is itself the credential, and a webhook's signing secret are sealed with the workspace key (AES-256-GCM, bound to the channel) and rewrapped when the key rotates. Settings show only the host, or a webhook's address without its query. The signing secret is shown once, when it is made.
- **Signed.** A webhook carries `Hekate-Signature: t=…,v1=…`, an HMAC-SHA256 of the time and the body, so a receiver can check who sent it and refuse an old one. The event's id is the same on every retry and replay, so a receiver can drop a repeat.
- **Nothing private.** Channels must be HTTPS. The server connects only to public addresses: the address checked is the address connected to (no DNS rebinding), an address given as a number is checked too, and redirects are not followed. An origin on a private network needs the operator to list it in `WEBHOOK_TRUSTED_ORIGINS`. Each request has ten seconds.
- **Logged.** Adding, changing and removing a channel are in the workspace's access log; every delivery and its attempts are in the instance's webhook log, and replaying one is an instance event.
- **A workspace's own mail.** Its provider's details, the secret among them, are sealed with the workspace key, rewrapped on rotation and never sent back. An SMTP server is connected to at the address that was checked as public (the certificate still checked against its name), and a Mailcoach address must be public each time it is reached, unless the operator trusts it. Mail that belongs to an account (password resets, sign-in codes for members) never goes through a workspace's mail. Setting, changing and removing it are in the access log.
- **Bounce reports.** `/api/hooks/mail/instance` and `/api/hooks/mail/workspaces/:id` take a provider's reports without a session, and act on one only once its signature holds against the secret the operator or the workspace gave: Svix HMAC for Resend, HMAC for Mailgun, ECDSA for SendGrid, basic authentication for SparkPost, each within five minutes where the provider signs a time; RSA for Amazon SES through Amazon SNS and for Postal, within an hour of the time each signs (kept on retries); HMAC for Mailcoach; a bearer token for Plunk, which signs nothing. SNS's signing certificate is fetched only from `sns.<region>.amazonaws.com` over HTTPS, a message must name the topic given (a genuine message for anyone else's topic is refused before anything is fetched), and a subscription is confirmed only at an address on the same hosts, once its signature holds. One that does not hold is refused and changes nothing. A workspace's reports stop only that workspace's mail; the instance's stop everyone's.

## API tokens

Scripts and tools reach the API with a token instead of a session (#198, decision 221): a member's own (Account, API tokens), or one of the workspace's service tokens (Settings, API and OAuth clients; owners and admins only).

- **One workspace, some scopes.** A token reaches the workspace it was made in and nothing else, and only what its scopes allow (`files:read`, `files:write`, `reviews:read`, `reviews:write`, `comments`, `downloads`, `workflows`, `org:read`). Which scope a call needs is one pure function (`scopeFor` in `packages/shared`), and a path it does not name is refused (403, `token_not_allowed`): signing in, accounts, settings, other tokens, the instance, playback and page renders, deleting or moving projects and calendar links. A token never mints, changes or revokes a token.
- **No more than its member.** A member's token acts as them, with their role and project roles as they are at each call; removed from the workspace or deleted, their tokens are revoked. A service token acts through an account of its own that belongs to no workspace and cannot sign in (its address is under the reserved `.invalid` domain), with an admin's reach within its scopes; what it makes is shown as the token's.
- **Shown once, stored hashed.** A token is 32 random bytes after a prefix (`hk_pat_`, `hk_svc_`) that secret scanners can find; only its hash is stored (scrypt at a low cost, as a token is 256 random bits), with its first characters to tell it apart. It is never logged, and making, changing and revoking one are in the access log by name and hint.
- **Expiry and revocation.** A token lasts 30, 90 or 365 days, or until revoked; an expired or revoked token is refused (401, `token_invalid`). A request with a token is judged on the token alone, never on a session cookie it also carries.
- **Media.** A token never reaches playback keys, segments or page renders, which stay bound to a browser's session. Originals leave only with the `downloads` scope, through the same download links as a member's: watermarked, logged, once, within five minutes, bound to the token.
- **Limits and the log.** Each token may make 600 calls a minute (429 with `Retry-After` past that). Every call it makes, refused or not, is in the API log with its path as asked (never its query or body), answer and time; operators read it in the instance's Logs, and each workspace's admins read their own in Settings, API.
- **The public API** (#197, decision 224) is the same routes under `/api/v1`, which answers only what `scopeFor` names and `404` for the rest, whoever asks; it adds no route and no way in. Its OpenAPI document (`/api/openapi.json`) is public, as it describes calls and holds no data, and is read from the routes, so it cannot list one a token may not make.

## OAuth clients and connected apps

Applications that act for many people connect with OAuth 2.1 (#447, decision 225): a workspace's owners and admins register them as clients (Settings, API and OAuth clients), and each member lets one in on the consent screen and sees it in Account, Connected apps.

- **An access token is an API token.** What a connected app is issued is an API token of its own kind (`hk_oat_`, an hour long), found by its hash, held to the client's workspace and checked by the same middleware: the same scopes (`scopeFor`), the member's role at each call, the same rate limit and the API log, never playback or page renders. No token reaches the consent screen or mints another.
- **PKCE for every client, S256 only.** A confidential client also proves itself with its secret (Basic or the body); a public one has none and is refused if it sends one. Codes last a minute and are spent before anything else is checked, so a wrong verifier or redirect address cannot be tried twice; a code or refresh token used a second time revokes every token of its connection, as it may have been stolen.
- **Redirect addresses matched exactly**, except the port at a loopback IP address (RFC 8252). Only https, http on the person's own computer and an application's own scheme can be registered; never `javascript:`, `data:`, `file:` or an address with a fragment. An unknown client, or an address it did not register, is refused on the screen and never sent anywhere; every answer carries the issuer (`iss`, RFC 9207) and the application's `state`.
- **The consent screen** is a page of Hekate's own, under the same Content Security Policy (`frame-ancestors 'none'`, so it cannot be framed into a click). It names the application, the workspace and where the answer goes, and is refused to anyone who is not a member of the client's workspace, or whose sign-in falls short of what it asks (a second factor, single sign-on), or whose workspace is suspended. The answer is posted as JSON with the session, which a form on another site cannot send.
- **Hashed, shown once.** A client's secret (`hk_cls_`), codes (`hk_oac_`) and refresh tokens (`hk_ort_`) are 32 random bytes kept only as hashes, made as an API token's is; the client id is public. The secret is shown when the client is made or its secret rotated, and never logged; rotating stops the old one at once. The workspace export leaves secrets, codes and refresh tokens out.
- **Refresh tokens once each.** A refresh token lasts 30 days and works once, the answer carrying the next; it can narrow the scopes of an access token, never widen them. Revocation (RFC 7009) answers the same whatever the token, and a client can revoke only its own.
- **Ending a connection ends its tokens.** Disconnecting, leaving the workspace, deleting the account, deleting the client, or a client losing a scope (which every connection and live token loses at once) revokes the tokens at once. Registering, changing, rotating and deleting a client, and connecting and disconnecting an app, are in the access log.
- **Limits.** The token and revocation endpoints take 120 requests a minute from one address, answer any origin (a browser application is a public client) without credentials, and are never cached.

## The MCP endpoint

Assistants reach Hekate over the Model Context Protocol at `/api/mcp` (#199, decision 231).

- **A token alone.** It takes an API token or an OAuth access token in `Authorization`, never a session cookie, and refuses a browser request from another origin (403). Without a working token it answers 401, naming its protected resource metadata (RFC 9728) so an OAuth client can find Hekate's authorisation server.
- **No more than the token.** Every tool is made of public API calls (`/api/v1`) made in-process with the same token, through the same middleware and routes: its scopes, its workspace, its member's role, the rate limit and the API log apply to each call, and `tools/list` shows only what its scopes allow. Nothing is queried beside the routes.
- **No media.** No tool plays, downloads or renders anything, whatever the token holds; answers are reshaped field by field, so no playback, download or storage address can leave, and a last pass drops any key that names an address or a secret.

## Headers and limits

- **Headers:** the app sets them on every response, so they hold behind any proxy. The Content Security Policy allows this origin alone: no inline or evaluated script, no style, font, image or request from elsewhere, `blob:` only where hls.js feeds MediaSource and runs its worker, and `frame-ancestors 'none'` (with `X-Frame-Options: DENY`), so no page can be framed. Also `nosniff`, `Referrer-Policy: strict-origin-when-cross-origin`, a `Permissions-Policy` that grants passkeys, full screen, autoplay, MIDI and the microphone to this origin and nothing else (the take log reads a recorder's timecode through MIDI or an audio input, asked for only when someone connects one, and nothing it hears leaves the browser), `Cross-Origin-Opener-Policy` and `Cross-Origin-Resource-Policy: same-origin` (a workspace's logo alone keeps a stricter policy of its own and may be shown across origins, as above), and HSTS when the public address is HTTPS (Caddy, terminating TLS, adds it too). The visual suite loads every screen under the policy and fails on any violation.
- **Request size:** a body is at most 2 MB, except an upload chunk, which has its own limit (Uploads); larger requests get 413.
- **Rate limits:** kept in PostgreSQL, so every replica counts the same requests (decision 051). Sign-in, reset codes and second-factor codes use Better Auth's limits, now stored in the database; opening guest links and trying their codes are limited to 30 per address in ten minutes; starting uploads to 120 a minute per member; content keys to 30 a minute per session. A refusal is 429 with `Retry-After`. Counts older than a day are purged hourly.

## The runtime image

One image runs Hekate: Node on Alpine Linux, every stage from the same image pinned by digest, with ffmpeg, Poppler, its fonts and Python (for the ADM renderer) added from Alpine's packages and every package upgraded at build (decision 244). It holds only the programs Hekate runs (node, ffmpeg, ffprobe, Poppler's pdfinfo, pdftoppm and pdftotext, and python3): no package manager (npm and apk are removed; apk's records stay so scanners still see every package), no shell (busybox and every applet go), and no setuid or setgid binary, and it runs as the unprivileged `node` user. Compose runs it with a read-only root filesystem, `/tmp` and the media work directory in memory (tmpfs), every Linux capability dropped and no new privileges. CI builds it, runs it that way with a smoke test (`scripts/image-smoke.mjs`), and scans it at every severity. Without a shell, inspect a running container with `docker exec app node -e '...'`, or a debug container beside it.

## Settled questions

- Commercial DRM is not needed yet; segments can be repackaged as CENC `cbcs` without re-encoding if it ever is (decision 022).
- Downloads are a per-reviewer permission (none, proxy, original), always watermarked and logged.
